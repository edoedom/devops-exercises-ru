# GitOps

Предпосылки: Git, декларативные манифесты, CI/CD и базовый Kubernetes. Цель — понимать контроль изменений и восстановление, а не только установить контроллер.

<details>
<summary>Чем GitOps отличается от запуска kubectl из CI?</summary>

По [OpenGitOps](https://opengitops.dev/) желаемое состояние декларативно, версионируется, автоматически извлекается агентом и непрерывно согласуется с фактическим. Однократный push из pipeline не даёт непрерывного reconciliation. Git сам по себе не делает процесс GitOps.
</details>

<details>
<summary>Что хранить в репозитории окружения?</summary>

Декларации желаемого состояния, неизменяемые ссылки на образы/пакеты и конфигурацию, необходимую для воспроизводимого рендера. Зафиксируйте также версии зависимостей Helm/Kustomize. Одинаковый commit с mutable image tag или внешней неприкреплённой зависимостью может давать разный результат.
</details>

<details>
<summary>Как drift связан с self-heal и prune?</summary>

Drift — отклонение фактического состояния. В Argo CD автоматическое устранение drift и удаление исчезнувших из источника ресурсов управляются отдельными опциями. Удаление объекта из Git не означает, что pruning уже включён. Перед массовым удалением проверяют diff и защиту важных ресурсов. [Argo CD auto-sync](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/).
</details>

<details>
<summary>Означает ли статус Synced, что сервис работает?</summary>

Нет. Совпадение желаемых ресурсов и runtime-здоровье — разные проверки. Нужны health/rollout, readiness и проверка пользовательского сценария; удачный apply не доказывает исправность зависимостей, данных и бизнес-операций.
</details>

<details>
<summary>Когда Git revert не является полноценным rollback?</summary>

При несовместимой миграции данных, необратимом внешнем действии, изменившемся секрете или недоступном старом образе. Откат конфигурации может вернуть только часть системы. Планируйте совместимые expand/contract миграции, критерии отката и восстановление данных отдельно.
</details>

<details>
<summary>Как обращаться с секретами и правами контроллера?</summary>

Не храните открытые секреты в Git; base64 не является шифрованием. Используйте подходящий управляемый механизм получения или расшифрования с отдельными правами и ротацией. Ограничьте доступ к источникам, namespace/cluster и целевым ресурсам; компрометация контроллера не должна автоматически давать доступ ко всем окружениям.
</details>

<details>
<summary>Как выглядит promotion между окружениями?</summary>

Один проверенный артефакт продвигают по digest, меняя декларацию окружения через review и policy checks. Отдельная пересборка «того же релиза» для production создаёт другой артефакт. Условия согласования и автоматизации зависят от риска и команды.
</details>

<details>
<summary>Разберите ситуацию: после ручного исправления проблема возвращается.</summary>

Сравните фактический объект с источником и настройками reconciliation. Контроллер мог корректно вернуть старое желаемое состояние. Исправьте декларацию через согласованный процесс. В аварии допускается явно оформленная приостановка автоматизации с владельцем и сроком; после восстановления устраните drift и возобновите контроль.
</details>
