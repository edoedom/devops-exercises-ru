<a id="network"></a>
## Сети

<details>
<summary>Что в общем случае необходимо для общения?</summary><br><b>

  * Общий язык, понятный обеим сторонам.
  * Способ указать адресата.
  * Канал связи, по которому сообщение дойдёт до получателя.

</b></details>

<details>
<summary>Что такое TCP/IP?</summary><br><b>

Набор протоколов, определяющих взаимодействие устройств в сети.

Подробнее о TCP/IP — [здесь](http://www.penguintutor.com/linux/basic-network-reference).

</b></details>

<details>
<summary>Что такое Ethernet?</summary><br><b>

Семейство технологий локальных сетей. LAN объединяет устройства на относительно небольшой территории, например дома, в офисе или кампусе; WAN охватывает более крупные территории.

</b></details>

<details>
<summary>Что такое MAC-адрес и для чего он нужен?</summary><br><b>

Адрес сетевого интерфейса на канальном уровне. Его используют для доставки кадров в пределах канального сегмента; абсолютная уникальность не гарантирована.

Кадр Ethernet содержит MAC-адреса отправителя и получателя. При приёме интерфейс проверяет адрес назначения с учётом режима работы, широковещания и групповых адресов.

</b></details>

<details>
<summary>Когда используется ff:ff:ff:ff:ff:ff?</summary><br><b>

Это широковещательный MAC-адрес Ethernet. Кадр доставляется устройствам широковещательного домена; например, так передаются запросы ARP для поиска MAC по IPv4.
</b></details>

<details>
<summary>Что такое IP-адрес?</summary><br><b>

Числовой адрес интерфейса в сети IP. Он идентифицирует сетевую точку и позволяет маршрутизировать к ней пакеты.
</b></details>

<details>
<summary>Что такое маска подсети? Приведите пример.</summary><br><b>

32-битная маска IPv4 разделяет адрес на сетевую и узловую части: единицы обозначают сеть, нули — узел. Например, /24 соответствует 255.255.255.0. В обычной подсети первый адрес обозначает сеть, последний — широковещание; существуют исключения, например /31 для двухточечных связей.

[Пример](https://github.com/philemonnwanne/projects/tree/main/exercises/exe-09).

</b></details>

<details>
<summary>Что такое приватный IP и когда он используется?</summary><br><b>
Адрес из диапазона для частных сетей, не маршрутизируемый в публичном интернете. Он подходит для внутренних сервисов: например, игрового сервера в сети общежития. Доступ из другой частной сети возможен при настройке маршрутов или VPN.
</b></details>

<details>
<summary>Что такое публичный IP и когда он используется?</summary><br><b>
Глобально маршрутизируемый адрес. Чтобы друзья из интернета подключились к игровому серверу за домашним маршрутизатором, обычно нужны публичный адрес, разрешающие правила и перенаправление порта на внутренний сервер. Для участников той же локальной сети достаточно приватного адреса.
</b></details>

<details>
<summary>Опишите уровни OSI и их назначение.</summary><br><b>

* Прикладной: сетевые функции приложений, например HTTP.
* Представления: формат и преобразование данных, включая кодирование и шифрование в концептуальной модели.
* Сеансовый: создание, управление и завершение сеансов.
* Транспортный: передача данных между конечными узлами; TCP и UDP.
* Сетевой: адресация и маршрутизация пакетов; IP.
* Канальный: доставка кадров в канальном сегменте; MAC-адреса.
* Физический: электрические и физические характеристики передачи битов.

Подробнее — [на penguintutor.com](http://www.penguintutor.com/linux/basic-network-reference).
</b></details>

<details>
<summary>К каким уровням OSI относятся следующие понятия?

  * Исправление ошибок.
  * Маршрутизация пакетов.
  * Кабели и электрические сигналы.
  * MAC-адрес.
  * IP-адрес.
  * Завершение сеанса.
  * Трёхстороннее рукопожатие TCP.</summary><br><b>
  * Обработка ошибок — в том числе канальный уровень; это не исключительная функция одного уровня.
  * Маршрутизация — сетевой.
  * Кабели и сигналы — физический.
  * MAC-адрес — канальный.
  * IP-адрес — сетевой.
  * Управление сеансом — сеансовый; завершение TCP относится к транспортному.
  * Рукопожатие TCP — транспортный.
</b></details>

<details>
<summary>Какие схемы доставки данных вы знаете?</summary><br><b>

Unicast: один отправитель и один получатель.

Broadcast: всем устройствам широковещательного домена; MAC назначения — ff:ff:ff:ff:ff:ff.
Широковещание используют, например, ARP и некоторые сообщения DHCP.

Multicast: доставка группе подписчиков; возможны модели «один ко многим» и «многие ко многим».
</b></details>

<details>
<summary>Что такое CSMA/CD? Применяется ли он в современных Ethernet-сетях?</summary><br><b>

Carrier Sense Multiple Access with Collision Detection — множественный доступ с прослушиванием несущей и обнаружением коллизий.
Он управляет общей средой, где одновременно передаёт один узел. В современном коммутируемом полнодуплексном Ethernet коллизий такого типа нет, и CSMA/CD не используется.

Алгоритм CSMA/CD:

1. Перед отправкой проверить, свободна ли среда.
2. Если свободна — начать передачу.
3. Одновременная передача двух узлов вызывает коллизию.
4. Узлы отправляют jam-сигнал и прекращают передачу кадра.
5. Выжидают случайный интервал.
6. Повторяют попытку по тем же правилам.
</b></details>

<details>
<summary>Опишите устройства и различия между ними:

  * Маршрутизатор.
  * Коммутатор.
  * Концентратор.</summary><br><b>

Все три соединяют сетевые устройства, но работают на разных уровнях и по-разному передают данные.

1. Маршрутизатор соединяет IP-сети на уровне 3. Он выбирает следующий узел по таблице маршрутизации, формируемой статически и/или протоколами маршрутизации.
2. Коммутатор соединяет устройства LAN на уровне 2, изучает MAC-адреса и пересылает кадры в нужный порт. Разделение портов устраняет общую среду передачи, характерную для концентратора; существуют и коммутаторы с функциями уровня 3.
3. Концентратор работает на уровне 1 и повторяет сигнал на остальных портах, не анализируя адрес получателя. Все устройства делят среду и домен коллизий, поэтому производительность ниже. В современных сетях концентраторы практически заменены коммутаторами.
</b></details>

<details>
<summary>Что такое домен коллизий?</summary><br><b>
Сегмент общей среды, в котором одновременные передачи могут столкнуться и повредить данные. Устройства делят пропускную способность; в полнодуплексных коммутируемых соединениях таких коллизий нет.
</b></details>

<details>
<summary>Что такое широковещательный домен?</summary><br><b>
Область сети, в пределах которой распространяются широковещательные кадры. Их получают все устройства этой области, а не один заданный адресат.
</b></details>

<details>
<summary>Три компьютера подключены к коммутатору. Сколько доменов коллизий и широковещания?</summary><br><b>

В классической терминологии — три отдельных домена коллизий и один широковещательный домен, если все порты в одной VLAN. В полном дуплексе коллизий нет.
</b></details>

<details>
<summary>Как работает маршрутизатор?</summary><br><b>

Физическое или виртуальное устройство принимает IP-пакет, проверяет адрес назначения, выбирает подходящий маршрут и пересылает пакет в следующую сеть.

</b></details>

<details>
<summary>Что такое NAT?</summary><br><b>

Network Address Translation — преобразование IP-адресов пакетов, например приватных адресов в публичные для доступа в интернет, с обратным преобразованием ответов.

</b></details>

<details>
<summary>Что такое прокси, как он работает и зачем нужен?</summary><br><b>

Прокси — посредник между клиентом и целевым сервисом, например веб-сайтом.

Клиент обращается к прокси, тот отправляет запрос целевому серверу и передаёт ответ клиенту. Точная схема зависит от типа прокси.

Прокси применяют для контроля доступа, фильтрации, кэширования и других задач; свойства безопасности и приватности зависят от настройки.
</b></details>

<details>
<summary>Что такое TCP и трёхстороннее рукопожатие?</summary><br><b>

TCP предоставляет надёжный упорядоченный поток байтов. Перед передачей стороны устанавливают соединение трёхсторонним рукопожатием.

Основные шаги:

* Клиент отправляет серверу сегмент SYN с начальным номером последовательности.
* Сервер, принимающий соединения на указанном порту, отвечает SYN/ACK.
* Клиент подтверждает ответ сегментом ACK.
</b></details>

<details>
<summary>Что такое RTT?</summary><br><b>

По [Wikipedia](https://en.wikipedia.org/wiki/Round-trip_delay), это время прохождения сигнала к получателю и получения ответного подтверждения.

Дополнительный вопрос: какой RTT характерен для LAN?
</b></details>

<details>
<summary>Как происходит рукопожатие SSL/TLS?</summary><br><b>
Оно согласует защищённое соединение. SSL устарел; ниже — упрощённый сценарий TLS до версии 1.3 с исправлением ошибок исходника. Конкретные сообщения зависят от версии и обмена ключами.

1. ClientHello передаёт поддерживаемые версии, криптографические наборы, расширения и случайное значение клиента.
2. ServerHello сообщает выбранные параметры и случайное значение сервера.
3. Сервер передаёт сертификат, если используется сертификатная аутентификация.
4. Передаёт необходимые параметры обмена ключами и ServerHelloDone для соответствующих сценариев TLS 1.2.
5. Клиент проверяет сертификат и отправляет данные обмена ключами. Это не обязательно его открытый ключ.
6. Стороны вычисляют сеансовые ключи; клиент переключается на согласованную защиту через ChangeCipherSpec в соответствующем протоколе.
7. Клиент отправляет Finished, подтверждающий целостность рукопожатия. Это не сообщение с pre-master secret, как ошибочно указано в исходнике.
8. Сервер также переключается на согласованную защиту.
9. Сервер отправляет Finished. Он не возвращает клиенту pre-master secret.
10. Стороны обмениваются защищёнными данными приложения.
</b></details>

<details>
<summary>Чем TCP отличается от UDP?</summary><br><b>

TCP устанавливает соединение и обеспечивает упорядоченную доставку потока с повторной передачей потерь. UDP отправляет отдельные дейтаграммы без таких гарантий и без собственного рукопожатия. Это уменьшает накладные расходы и позволяет приложению выбирать собственную обработку потерь, что полезно, например, для потокового медиа.

Подробнее — [на Penguintutor.com](http://www.penguintutor.com/linux/basic-network-reference).
</b></details>

<details>
<summary>Какие протоколы стека TCP/IP вы знаете?</summary><br><b>

Например, Ethernet на канальном уровне, IP/ICMP на сетевом, TCP/UDP на транспортном, DNS, HTTP, SMTP и SSH на прикладном. TCP/IP — стек, а не один протокол; уровни его практической модели не всегда совпадают с семиуровневой OSI.
</b></details>

<details>
<summary>Что такое шлюз по умолчанию?</summary><br><b>

Маршрутизатор, которому узел отправляет пакеты, если нет более специфичного маршрута к назначению.
</b></details>

<details>
<summary>Что такое ARP и как он работает?</summary><br><b>

Address Resolution Protocol сопоставляет IPv4 и MAC в локальном сегменте. Например, перед отправкой на 192.168.1.1 узел узнаёт MAC этого адреса через широковещательный запрос ARP.

Результат сохраняется в таблице соседей. Пока подходящая запись действительна, повторный запрос не нужен.
</b></details>

<details>
<summary>Что такое TTL и что он предотвращает?</summary><br><b>

* Поле IPv4 Time to Live ограничивает число маршрутизаторов на пути. При пересылке оно уменьшается; при исчерпании пакет отбрасывается, обычно с ICMP Time Exceeded отправителю.
* Это предотвращает бесконечное обращение пакетов и связанную перегрузку.
* В частности, ограничивает последствия петель маршрутизации.
* TTL может использоваться дополнительными механизмами проверки близости соседа, но сам по себе не защищает от подмены IP. Утверждение исходника об общей защите от spoofing неточно.
</b></details>

<details>
<summary>Что такое DHCP и как он работает?</summary><br><b>

Dynamic Host Configuration Protocol выдаёт сетевые настройки: адрес, маску, шлюз и другие параметры. Типичный начальный обмен DHCPv4:

* Клиент ищет сервер широковещательным DHCPDISCOVER.
* Сервер предлагает адрес и параметры аренды сообщением DHCPOFFER.
* Клиент выбирает предложение и отправляет DHCPREQUEST.
* Сервер подтверждает аренду DHCPACK.

Подробнее — [здесь](https://linuxjourney.com/lesson/dhcp-overview).
</b></details>

<details>
<summary>Можно ли иметь два DHCP-сервера в одной сети?</summary><br><b>

Да, это распространённый вариант отказоустойчивости, если серверы согласованно настроены.
* Несогласованные пулы могут выдавать один адрес разным клиентам; разные параметры шлюза и DNS также вызывают проблемы. Само получение нескольких предложений клиентом допустимо.
* Используют непересекающиеся диапазоны либо механизм failover с координацией аренд; также можно обслуживать разные подсети.
</b></details>

<details>
<summary>Что такое SSL/TLS-туннель и как он работает?</summary><br><b>

* Трафик одного протокола передаётся внутри защищённого TLS-соединения через недоверенную сеть. TLS обеспечивает конфиденциальность, целостность и проверку стороны или обеих сторон в зависимости от конфигурации.

Основные шаги:

1. Клиент начинает TLS-рукопожатие с сервером.
2. Во время рукопожатия стороны согласуют параметры, проверяют сертификаты согласно выбранной схеме и получают ключи. Это происходит до защищённого обмена, а не после него.
3. Клиент передаёт трафик в туннель; сервер расшифровывает и направляет его целевому сервису.
4. Ответ передаётся обратно через туннель и поступает приложению клиента.
</b></details>

<details>
<summary>Что такое сокет? Как посмотреть сокеты системы?</summary><br><b>

* Сокет — программная конечная точка обмена данными. Он предоставляет интерфейс взаимодействия процессов по сети или локально. Пример команды Linux:
`netstat -an`
* Вывод показывает протоколы, локальные и удалённые адреса и состояния. Также можно использовать `ss -an`.
</b></details>

<details>
<summary>Что такое IPv6 и зачем он нужен при наличии IPv4?</summary><br><b>

* IPv6 использует 128-битные адреса, например 2001:0db8:85a3:0000:0000:8a2e:0370:7334, вместо 32-битных IPv4.

Причины внедрения:

1. Значительно большее адресное пространство: IPv4 недостаточно для глобального роста числа устройств.
2. Поддержка IPsec, хотя она есть и у IPv4 и не означает шифрования всего IPv6-трафика по умолчанию.
3. Возможности групповой доставки и организации сети; IPv6 не гарантирует автоматически более высокую скорость.
4. Автоконфигурация SLAAC позволяет получать адреса без DHCPv6.
5. Механизмы мобильности, например Mobile IPv6, для сохранения связности при перемещении между сетями.
</b></details>

<details>
<summary>Что такое VLAN?</summary><br><b>

* Логический широковещательный домен поверх физической сети. Коммутаторы относят порты и кадры к VLAN; при передаче нескольких VLAN по одному каналу обычно используется тег 802.1Q.
</b></details>

<details>
<summary>Что такое MTU?</summary><br><b>
	
Maximum Transmission Unit — максимальный размер блока данных, передаваемого на соответствующем уровне без фрагментации; для IP обычно говорят о максимальном размере IP-пакета на интерфейсе.
</b></details>

<details>
<summary>Что произойдёт с пакетом больше MTU?</summary><br><b>
	
В IPv4 маршрутизатор может фрагментировать пакет, если это не запрещено флагом DF; иначе отбрасывает его и сообщает об ошибке.
	
В IPv6 маршрутизатор не фрагментирует пакет и отправляет ICMPv6 Packet Too Big; размер должен скорректировать отправитель.
</b></details>

<details>
<summary>Верно ли, что ping использует UDP, поскольку надёжное соединение ему не нужно?</summary><br><b>

Неверно. Обычный ping использует ICMP Echo Request и Echo Reply.
</b></details>

<details>
<summary>Что такое SDN?</summary><br><b>

* Software-Defined Networking — программно управляемая сеть, в которой управление абстрагировано от конкретных устройств.
* SDN отделяет принятие решений control plane от пересылки data plane и позволяет управлять ими через логически централизованный контроллер вместо настройки каждого устройства по отдельности.
</b></details>

<details>
<summary>Что такое ICMP и зачем он нужен?</summary><br><b>

* Internet Control Message Protocol передаёт служебные и диагностические сообщения в IP-сетях.

Примеры применения:
1. Сообщения об ошибках доставки.
2. Проверка доступности и RTT с помощью ping.
3. Определение MTU пути без фрагментации.
4. Получение ответов для traceroute.
5. Обнаружение маршрутизаторов в соответствующих протоколах.
</b></details>

<details>
<summary>Как работает NAT?</summary><br><b>

NAT преобразует адреса, а NAPT/PAT — также порты, позволяя нескольким внутренним устройствам использовать один внешний IPv4. Это распространено в домашних и корпоративных сетях.
Например, источник 192.168.1.100 преобразуется в публичный адрес маршрутизатора. Удалённый сервер видит внешний адрес; таблица трансляций позволяет вернуть ответ нужному устройству.
</b></details>

<details>
<summary>Какие стандартные порты используют следующие протоколы?

  * SSH
  * SMTP
  * HTTP
  * DNS
  * HTTPS
  * FTP
  * SFTP
</summary><br><b>

  * SSH - 22
  * SMTP - 25
  * HTTP - 80
  * DNS - 53
  * HTTPS - 443
  * FTP - 21
  * SFTP - 22
</b></details>

<details>
<summary>Что влияет на производительность сети?</summary><br><b>

Основные факторы:

1. Ёмкость канала: недостаточная пропускная способность ограничивает скорость передачи и увеличивает очереди.
2. Задержка: особенно заметна в интерактивных приложениях, видеосвязи и играх.
3. Перегрузка: спрос превышает доступные ресурсы сети.
4. Потери: повторные передачи и восстановление снижают полезную скорость.
5. Топология: расположение устройств и построение путей.
6. Протоколы: подтверждения, контроль перегрузки и повторные передачи имеют свои издержки.
7. Средства защиты: фильтрация и шифрование потребляют ресурсы и могут добавлять задержку.
8. Расстояние и качество среды: распространение сигнала, помехи и уровень сигнала беспроводной сети.
</b></details>

<details>
<summary>Что такое APIPA?</summary><br><b>

Автоматическое назначение локального IPv4-адреса из link-local диапазона,
когда получить настройки через DHCP не удаётся.

</b></details>

<details>
<summary>Какой диапазон используется APIPA?</summary><br><b>

Диапазон IPv4 link-local — 169.254.0.0/16. Для автоматического выбора адреса используются 169.254.1.0–169.254.254.255; крайние /24 зарезервированы. Диапазон исходника неточен.

</b></details>

<a id="control-plane-and-data-plane"></a>
#### Управление и пересылка данных

<details>
<summary>Что такое control plane?</summary><br><b>

Компоненты, принимающие решения о маршрутах и правилах пересылки.
</b></details>

<details>
<summary>Что такое data plane?</summary><br><b>

Компоненты, непосредственно пересылающие пакеты по заданным правилам.
</b></details>

<details>
<summary>Что такое management plane?</summary><br><b>

Функции настройки, администрирования и мониторинга.
</b></details>

<details>
<summary>К какой плоскости относится построение таблиц маршрутизации?</summary><br><b>

К control plane.
</b></details>

<details>
<summary>Объясните Spanning Tree Protocol (STP).</summary><br><b>

STP выбирает корневой мост и логическую топологию без L2-петель, блокируя избыточные пути. После изменения топологии пути пересчитываются; RSTP ускоряет сходимость, MSTP объединяет VLAN в экземпляры. STP не заменяет маршрутизацию, а BPDU Guard и защита root помогают ограничивать ошибочные подключения.
</b></details>

<details>
<summary>Что такое агрегация каналов и зачем она нужна?</summary><br><b>

Несколько физических каналов объединяют в логический, например LAG с LACP. Это повышает суммарную ёмкость и/или резервирование; один поток обычно попадает на один участник по хешу и не получает сумму скоростей всех каналов. Обе стороны должны быть согласованно настроены.
</b></details>

<details>
<summary>Что такое асимметричная маршрутизация и как с ней работать?</summary><br><b>

Прямой и обратный трафик проходят разными путями. Это допустимо для IP, но может нарушать stateful firewall, NAT и строгий reverse-path filtering. Диагностируйте оба направления, таблицы маршрутов и состояние промежуточных устройств; исправляйте схему или настройки с учётом угроз, а не отключайте проверки вслепую.
</b></details>

<details>
<summary>Какие протоколы оверлейных сетей и туннелирования вы знаете?</summary><br><b>

GRE, VXLAN, Geneve, IP-in-IP, IPsec tunnel mode, WireGuard в соответствующих схемах. Не все они предоставляют шифрование и аутентификацию; отдельно учитывайте overhead, MTU и область маршрутизации.
</b></details>

<details>
<summary>Что такое GRE и как он работает?</summary><br><b>

Generic Routing Encapsulation помещает пакет одного протокола в другой сетевой пакет. Применяется для туннелей; обычный GRE не обеспечивает конфиденциальность или проверку отправителя. Защиту при необходимости добавляют другим механизмом, например IPsec.
</b></details>

<details>
<summary>Что такое VXLAN и как он работает?</summary><br><b>

VXLAN инкапсулирует Ethernet-кадры в UDP между VTEP; VNI идентифицирует логический L2-сегмент. Позволяет строить overlay поверх IP-underlay. Нужны достижимость VTEP, согласованный MTU и механизм изучения/распространения MAC, например EVPN; VXLAN сам не шифрует данные.
</b></details>

<details>
<summary>Что такое SNAT?</summary><br><b>

Source NAT меняет адрес источника, а при необходимости и порт, перед отправкой пакета. Таблица трансляций позволяет обработать ответ. Используется, например, для выхода приватных IPv4 в интернет; NAT не заменяет firewall и не является обязательным свойством маршрутизатора.
</b></details>

<details>
<summary>Объясните OSPF.</summary><br><b>


Open Shortest Path First — протокол внутренней маршрутизации с состоянием каналов. Поддерживается многими маршрутизаторами; версии OSPF обслуживают IPv4 и IPv6. Сеть делится на области, что ограничивает распространение подробной информации о топологии и помогает масштабированию.

Четыре роли маршрутизаторов OSPF:
  * Внутренний маршрутизатор области.
  * Пограничный маршрутизатор областей (ABR).
  * Пограничный маршрутизатор автономной системы (ASBR).
  * Маршрутизатор магистральной области.

Подробнее: https://www.educba.com/ospf-router-types/
</b></details>

<details>
<summary>Что такое задержка?</summary><br><b>
	
Время прохождения данных от источника к назначению.
</b></details>

<details>
<summary>Что такое пропускная способность канала (bandwidth)?</summary><br><b>
	
Предельная ёмкость передачи за единицу времени. Чем она выше, тем больше данных потенциально можно передать.
</b></details>

<details>
<summary>Что такое throughput?</summary><br><b>
	
Фактически достигнутая скорость передачи данных за определённый интервал.
</b></details>

<details>
<summary>Что важнее для поискового запроса: задержка или throughput? Как учесть это в глобальной инфраструктуре?
</summary><br><b>

Обычно задержка. Запрос стоит направлять в доступный ЦОД с малой сетевой задержкой и достаточными ресурсами.
</b></details>

<details>
<summary>Что важнее при загрузке видео: задержка или throughput? Как это обеспечить?</summary><br><b>

Обычно throughput. Нужен путь с достаточной свободной пропускной способностью.
</b></details>

<details>
<summary>Что ещё учитывать при выборе места обработки запроса?</summary><br><b>

* Наличие актуальных данных и содержимого кэша: ближайший ЦОД не всегда лучший выбор.
</b></details>

<details>
<summary>Что такое Spine–Leaf?</summary><br><b>
Двухуровневая топология сети ЦОД, предназначенная для масштабирования и предсказуемых коротких путей между серверами.

В ней два основных типа коммутаторов:

* Spine образуют магистраль. Каждый соединён со всеми Leaf.
* Leaf подключают серверы и хранилища и соединяются со всеми Spine. Между Leaf доступны равнозначные пути через Spine. Отсутствие переподписки зависит от ёмкости портов, а не гарантируется одним названием топологии.

Такая архитектура подходит для облаков, виртуализации и интенсивного обмена между серверами благодаря масштабируемости и избыточным путям.
</b></details>

<details>
<summary>Что такое перегрузка сети и почему она возникает?</summary><br><b>

Объём предлагаемых данных превышает возможности канала или устройства.</br>
Растут очереди, задержки и потери. Причины: всплески нагрузки, большие передачи, вредоносный трафик, неисправности и ошибки проектирования.</br>
Нужны мониторинг, достаточная ёмкость и механизмы управления нагрузкой.
</b></details>

<details>
<summary>Опишите формат UDP и TCP. Чем отличаются их заголовки?</summary><br><b>

Заголовок UDP фиксированно 8 байт: порты, длина, checksum. TCP имеет порты, sequence/acknowledgment numbers, flags, window, checksum и опции; минимальный заголовок 20 байт. TCP поддерживает соединение и поток с подтверждениями, UDP — отдельные дейтаграммы без таких гарантий. IPv4/IPv6 могут по-разному задавать требования checksum.
</b></details>

<details>
<summary>Что такое экспоненциальная задержка повторных попыток и где она применяется?</summary><br><b>

</b></details>

</b></details>

### Вопросы для самопроверки по ОС

<details>
<summary>Что такое операционная система?</summary><br><b>

По книге «Operating Systems: Three Easy Pieces»:

ОС упрощает запуск программ, создаёт видимость одновременного выполнения, распределяет память, обеспечивает работу с устройствами и другие базовые функции.
</b></details>

<a id="operating-system---process"></a>
#### ОС: процессы

<details>
<summary>Что такое процесс?</summary><br><b>

Экземпляр выполняемой программы с её адресным пространством, состоянием исполнения и ресурсами, которыми управляет ОС.
</b></details>

<details>
<summary>Какие операции вы включили бы в API управления процессами?</summary><br><b>

Например:

* Создание процесса.
* Завершение процесса.
* Получение состояния: выполняется, ожидает, остановлен и т. д.
* Приостановка выполнения.
</b></details>

<details>
<summary>Как создаётся процесс?</summary><br><b>

* ОС подготавливает код программы и необходимые данные.
* Создаёт адресное пространство и отображает в него исполняемый файл.
* Подготавливает стек, аргументы и окружение согласно ABI.
* Организует области для динамической памяти, например кучи.
* Настраивает ресурсы ввода-вывода; в Unix обычно доступны стандартные дескрипторы ввода, вывода и ошибок.
* Передаёт управление точке входа; библиотека запуска затем обычно вызывает `main()`, а не ядро напрямую.
</b></details>

<details>
<summary>Загружается ли вся программа в память сразу?</summary><br><b>

Не обязательно. Современные ОС обычно подгружают страницы по мере обращения, а не читают весь файл заранее.
</b></details>

<details>
<summary>Какие основные состояния процесса существуют?</summary><br><b>

* Running: исполняется на CPU.
* Ready: готов, но ожидает выделения CPU.
* Blocked: ожидает событие, например завершение ввода-вывода.
</b></details>

<details>
<summary>Из-за чего процесс может заблокироваться?</summary><br><b>

  * Ожидание дискового ввода-вывода.
  * Ожидание данных из сети.
</b></details>

<details>
<summary>Что такое IPC?</summary><br><b>

Inter-Process Communication — механизмы обмена данными и синхронизации между процессами.
</b></details>

<details>
<summary>Что такое разделение времени?</summary><br><b>

Даже один CPU может попеременно выполнять разные программы, создавая для пользователей видимость одновременной работы. ОС распределяет процессорное время между задачами.
</b></details>

<details>
<summary>Что такое пространственное разделение ресурсов?</summary><br><b>

Ресурс делится на области, одновременно выделенные разным потребителям, в отличие от поочерёдного использования одного ресурса во времени.<br>
Например, место на диске, занятое файлом, остаётся выделенным ему до освобождения.
</b></details>

<details>
<summary>Кто выбирает процесс для исполнения на CPU?</summary><br><b>

Планировщик процессора.
</b></details>

<a id="operating-system---memory"></a>
#### ОС: память

<details>
<summary>Что такое виртуальная память и зачем она нужна?</summary><br><b>

Абстракция адресного пространства процесса с отображением виртуальных адресов на физическую память. Она обеспечивает изоляцию и гибкое управление памятью. Часть страниц может выгружаться на диск, но виртуальная память не сводится к swap; больше RAM уменьшает необходимость медленной подкачки.
https://www.minitool.com/lib/virtual-memory.html
</b></details>

<details>
<summary>Что такое demand paging?</summary><br><b>

Загрузка страниц в физическую память по мере обращения. Это сокращает стартовые затраты и использование RAM, но первое обращение может вызвать page fault и дополнительную задержку.
</b></details>

<details>
<summary>Что такое copy-on-write?</summary><br><b>
Копирование при записи сокращает ненужное дублирование данных. Например, после `fork()` ОС может временно разделять физические страницы родителя и потомка.

Принцип:
1. Пока стороны только читают, они используют общие страницы, помеченные как доступные только для чтения.
У каждого процесса собственное отображение адресов на эти страницы.
2. Прямая запись в общую страницу изменила бы данные у остальных процессов.
Это нарушило бы ожидаемую независимость, например при изменении переменных стека или кучи после `fork()`.
3. Поэтому при попытке записи ОС сначала создаёт отдельную копию страницы для записывающего процесса, а затем разрешает изменение.
</b></details>

<details>
<summary>Что такое ядро и что оно делает?</summary><br><b>

Ядро — часть ОС, отвечающая, в частности, за:

  * Распределение памяти.
  * Планирование процессов.
  * Управление выполнением на CPU.
</b></details>

<details>
<summary>Верно ли, что память ядра защищена от перезаписи обычными приложениями?</summary><br><b>

Верно.
</b></details>

<details>
<summary>Что такое POSIX?</summary><br><b>

Portable Operating System Interface — семейство стандартов интерфейсов Unix-подобных ОС и приложений.
</b></details>

<details>
<summary>Что такое семафор и для чего он нужен?</summary><br><b>

Примитив синхронизации со счётчиком, который управляет доступом процессов или потоков к ресурсам либо используется для сигнализации о событиях.
</b></details>

<details>
<summary>Чем кэш отличается от буфера?</summary><br><b>

Кэш хранит копии данных для ускорения повторного доступа, например чтения с диска.
Буфер временно накапливает данные при передаче или обработке, например для согласования скоростей производителя и потребителя.
</b></details>

<a id="prometheus"></a>
## Prometheus

<details>
<summary>Что такое Prometheus и каковы его основные возможности?</summary><br><b>

Открытая система сбора метрик и оповещения, первоначально разработанная в SoundCloud. Она хранит временные ряды и предоставляет язык PromQL для запросов и анализа; широко применяется для микросервисов и облачной инфраструктуры.

Основные возможности:

1. Многомерная модель: временной ряд определяется именем метрики и набором меток, например сервиса и окружения.

2. Pull-модель: сервер периодически опрашивает endpoints метрик. Её удобство и надёжность зависят от архитектуры; она не всегда превосходит push.

3. База временных рядов: хранит образцы, поддерживает диапазонные запросы и агрегации.

4. Правила оповещения: Prometheus определяет состояния, а Alertmanager группирует и направляет уведомления в почту, чат и другие каналы.

5. Интерфейс запросов и графиков; для панелей часто используют Grafana. Упомянутый в исходнике PromDash — исторический проект, а не актуальная встроенная панель.

Prometheus подходит для анализа поведения систем по метрикам и построения мониторинга и оповещений.

</b></details>

<details>
<summary>Когда Prometheus может не подойти?</summary><br><b>

Когда нужна стопроцентная точность учёта каждого события, например для расчёта оплаты за каждый запрос.
</b></details>

<details>
<summary>Опишите архитектуру Prometheus.</summary><br><b>

Основные компоненты:

1. Сервер Prometheus опрашивает цели, хранит временные ряды и вычисляет запросы и правила.

2. Клиентские библиотеки позволяют приложениям публиковать метрики; доступны для Go, Python, Java и других языков.

3. Экспортёры преобразуют показатели сторонних систем, например MySQL, PostgreSQL и Apache, в формат метрик.

4. Alertmanager устраняет дубликаты, группирует и маршрутизирует оповещения.

Для крупных сред используют несколько серверов и дополнительные средства хранения и запросов. Отказоустойчивость и масштабирование требуют отдельного проектирования.
</b></details>

<details>
<summary>Сравните Prometheus, InfluxDB и другие системы мониторинга.</summary><br><b>

Prometheus ориентирован на мониторинг метрик, метки, PromQL и pull-сбор. InfluxDB — база временных рядов с собственными интерфейсами записи и запросов; возможности зависят от версии. Их нельзя надёжно разделить на «быстрый» и «простой» без требований и измерений.

Nagios традиционно ориентирован на проверки состояния узлов и сервисов. Он поддерживает активные и пассивные проверки, поэтому описание его как исключительно push-системы в исходнике неточно.

Выбор зависит от источников данных, запросов, требований к хранению, оповещениям, эксплуатации и масштабу, а не только от размера организации.
</b></details>

<details>
<summary>Что такое alert?</summary><br><b>
Состояние, возникающее при выполнении условия правила над метриками. После предусмотренной задержки оно может перейти в firing; Alertmanager отправляет уведомления ответственным. Правила должны помогать своевременно обнаруживать проблемы и предпринимать действия.
</b></details>

<details>
<summary>Что такое instance и job?</summary><br><b>

Instance — отдельная цель опроса, например endpoint сервиса. Job — группа целей с одинаковой функцией, например экземпляры одного веб-приложения.

Иными словами, instance идентифицирует отдельную цель, job объединяет похожие цели.
</b></details>

<details>
<summary>Какие основные типы метрик поддерживает Prometheus?</summary><br><b>
Основные типы:

1. Counter: счётчик, растущий до сброса, например число запросов или ошибок.

2. Gauge: значение, которое может увеличиваться и уменьшаться, например занятая память.

3. Histogram: распределение наблюдений по диапазонам (buckets), а также их количество и сумма; подходит для задержек и размеров ответов.

4. Summary: количество и сумма наблюдений, а при настройке — квантили, вычисленные на стороне приложения.

PromQL предоставляет операции и функции, например `sum`, `max`, `min` и `rate`, для анализа и агрегации рядов.
</b></details>

<details>
<summary>Что такое экспортёр и зачем он нужен?</summary><br><b>
Экспортёр связывает стороннюю систему с Prometheus, предоставляя её показатели в поддерживаемом формате.

Он собирает показатели и публикует их через HTTP endpoint, который опрашивает Prometheus.

Экспортёры существуют для БД, веб-серверов, хранилищ и других компонентов, например MySQL, PostgreSQL, Apache и Nginx.

Они позволяют подключать к мониторингу системы без встроенной инструментализации Prometheus.
</b></details>

<details>
<summary>Какие практики Prometheus вы рекомендуете?</summary><br><b>
Например:

1. Последовательные имена и метки. Ограничивайте кардинальность: не используйте неограниченные идентификаторы пользователей или запросов как метки.

2. Понятные метрики, каждая из которых измеряет определённое свойство системы.

3. Оповещения, требующие действия. Избыточный шум вызывает усталость; пороги и длительность следует настраивать по реальному поведению системы.
</b></details>

<details>
<summary>Как получить количество запросов за период?</summary><br><b>

Для счётчика используйте `increase`, затем сложите ряды:

```promql
sum(increase(http_requests_total[1h]))
```

Это оценка количества запросов за час с учётом сбросов счётчика и экстраполяции. `sum(rate(...[1h]))` вернул бы среднюю скорость в секунду, а не количество. Для суток замените `1h` на `1d`.
</b></details>

<details>
<summary>Что означает HA для Prometheus?</summary><br><b>

Высокая доступность мониторинга при отказах. Типичный вариант — два независимых Prometheus, опрашивающих одни цели. Они не синхронизируют локальные базы автоматически; устранение дубликатов оповещений и объединение данных решаются Alertmanager и дополнительными компонентами.
</b></details>

<details>
<summary>Как соединить две метрики?</summary><br><b>

Бинарной операцией с сопоставлением по меткам. Например, доля ошибок для каждого сочетания service и instance:

```promql
sum by (service, instance) (rate(error_count_total[5m]))
/
on (service, instance)
sum by (service, instance) (rate(request_count_total[5m]))
```

Обе метрики должны быть счётчиками с одинаковой областью учёта. Агрегация даёт один ряд на ключ. Нулевой знаменатель и отсутствующие ряды требуют решения по смыслу задачи. `group_left`/`group_right` нужны при допустимом сопоставлении many-to-one; функции `join()` и `sum_series()` в PromQL нет.
</b></details>

<details>
<summary>Как получить значения метки?</summary><br><b>
Через API значений меток Prometheus или механизм переменных Grafana. `label_values` не является функцией PromQL.

Ниже приведён пример из исходника для `method` метрики `http_requests_total`; его следует трактовать как синтаксис инструмента переменных, а не исполняемый PromQL:

```
label_values(http_requests_total, method)
```

Полученный список можно использовать для выбора фильтра. Для API важно задавать подходящие селекторы и временной интервал.
</b></details>

<details>
<summary>Как перевести process_cpu_seconds_total в процент CPU?</summary><br><b>

Для процесса `rate(process_cpu_seconds_total[5m])` показывает число занятых ядер, усреднённое за пять минут. Процент одного ядра:

```promql
100 * rate(process_cpu_seconds_total{job="my-job"}[5m])
```

Процесс, использующий два ядра, может дать 200%. Если процессу доступны ровно четыре ядра и нужен процент этой ёмкости:

```promql
100 * rate(process_cpu_seconds_total{job="my-job"}[5m]) / 4
```

Не делите результат `rate` повторно на `5m`: функция уже нормализует счётчик по времени. Для метрики только user-mode расчёт покажет лишь пользовательское время; для загрузки всего хоста используйте соответствующие node-метрики. Число доступных ядер учитывает ограничения контейнера и не всегда равно ядрам хоста.

[Функции PromQL](https://prometheus.io/docs/prometheus/latest/querying/functions/).
</b></details>

<details>
<summary>Чем отличаются <code>var x int = 2</code> и <code>x := 2</code>?</summary><br><b>

В обоих случаях создаётся целочисленная переменная со значением 2.

Первый вариант явно указывает тип. Второй использует вывод типа и краткое объявление, допустимое внутри функции.
</b></details>

<details>
<summary>Верно ли, что в Go можно повторно объявлять переменные и каждую объявленную переменную нужно использовать?</summary>

Повторное объявление зависит от области и формы: `:=` допускает уже существующие переменные при наличии хотя бы одной новой, возможно и затенение во вложенной области. Неиспользуемые локальные переменные вызывают ошибку; исходный ответ чрезмерно обобщён.
</b></details>

<details>

<details>
<summary>Что не так в следующем коде и как исправить?

```

    var x float32 = 13.5

    y = x

```
</summary><br><b>

Go не присваивает float32 переменной int неявно. Используйте `y = int(x)` с осознанной потерей дробной части, затем, например, `fmt.Println(y)` с импортом fmt, иначе неиспользуемая локальная y тоже вызовет ошибку. Преобразование к int отбрасывает дробную часть к нулю, а не округляет до ближайшего.
</b></details>

<details>
<summary>Почему преобразование числа 101 в строку даёт «e», а не «101»? Как исправить?

    y = string(x)

}
```
</summary><br><b>

Преобразование `string(x)` трактует целое число как кодовую точку Unicode; 101 соответствует `e`.

<details>

}
```
</summary><br><b>

Константы Go инициализируются только константными выражениями.
Здесь `x`, `y` и их сумма — переменные значения.

<details>
<summary>Что выведет следующий код?

	"fmt"

		a[i] = 5
	}

	fmt.Println("1:", a)

	for i := range a {

	}

## Mongo

<details>
<summary>Каковы преимущества MongoDB перед другими NoSQL-системами?</summary><br><b>

Возможные преимущества при подходящей задаче:
* Гибкая схема документов.
* Горизонтальное масштабирование.
* Возможность хранить связанные данные вместе и уменьшать потребность в соединениях.
* Понятная структура отдельного документа.

</b></details>

<details>
<summary>Чем SQL-БД отличаются от NoSQL?</summary><br><b>

Реляционные СУБД организуют данные в таблицы со строками,
столбцами, связями и ограничениями. NoSQL — общее название
других моделей: ключ–значение, документы, графы и т. д.
Называть все NoSQL-данные неструктурированными неправильно: у них тоже есть структура, но она устроена иначе.
</b></details>

<details>
<summary>Когда предпочесть MongoDB или другую NoSQL-СУБД реляционной?</summary><br><b>

* Когда данные естественно представляются неоднородными документами и схема часто меняется.
* Когда выбранная модель согласованности отвечает требованиям. NoSQL не означает обязательного отсутствия целостности.
* Когда нужны подходящие механизмы горизонтального масштабирования.
</b></details>

<details>
<summary>Что такое документ и коллекция?</summary><br><b>

* Документ — запись MongoDB в формате BSON, базовая единица хранения.
* Коллекция — группа документов в базе данных.
</b></details>

<details>
<summary>Что такое агрегация MongoDB?</summary><br><b>

* Обработка набора документов для фильтрации, преобразования, группировки и вычисления результатов.
</b></details>

<details>
<summary>Что лучше: вложенные документы или ссылки?</summary><br><b>

* Зависит от запросов и модели данных. Вложение удобно для совместного чтения и атомарного изменения документа; ссылки уменьшают дублирование и поддерживают независимые сущности.
</b></details>

<details>
<summary>Как вы оптимизировали чтение MongoDB? Что можно сделать с медленным запросом?</summary><br><b>

* Проверить план, индексы, схему документов, фильтры и объём возвращаемых данных; затем рассмотреть распределение нагрузки.
</b></details>

<details>
<summary>Объясните запрос <code>db.books.find({"name": /abc/})</code>.</summary><br><b>

Ищет документы коллекции books, где поле name соответствует регулярному выражению abc. Без якорей это совпадение подстроки; регистр по умолчанию учитывается. Использование индекса и стоимость зависят от формы regex, индекса и collation.
</b></details>

<details>
<summary>Объясните запрос <code>db.books.find().sort({x:1})</code>.</summary><br><b>

Возвращает курсор документов books, отсортированных по x по возрастанию. Для стабильного порядка при одинаковом x добавьте уникальное поле сортировки, например _id; большое сортирование без подходящего индекса может быть дорогим.
</b></details>

<details>
<summary>Чем отличаются find() и find_one()?</summary><br><b>
	
* `find()` возвращает курсор для документов, соответствующих условию.
* `find_one()` возвращает один документ или значение отсутствия результата, зависящее от драйвера.
</b></details>

### Самопроверка SQL

<details>
<summary>Что такое SQL?</summary><br><b>

Structured Query Language — язык работы с реляционными БД, например MySQL и MariaDB.<br>
Позволяет читать, создавать, изменять и удалять данные, а также управлять схемой и доступом.
</b></details>

<details>
<summary>Чем SQL отличается от NoSQL?</summary><br><b>

Реляционные СУБД организуют данные в таблицы со строками,
столбцами, связями и ограничениями. NoSQL — общее название
других моделей: ключ–значение, документы, графы и т. д.
Называть все NoSQL-данные неструктурированными неправильно: у них тоже есть структура, но она устроена иначе.
</b></details>

<details>
<summary>Когда выбирать реляционную БД, а когда NoSQL?</summary><br><b>

Реляционная БД часто удобна при сложных связях и строгих требованиях целостности.
Транзакции ACID полезны, например, в финансовых системах, но доступны не только реляционным СУБД.

NoSQL может подходить для определённой модели данных и горизонтального масштабирования.
Некоторые такие системы удобны для распределения данных между серверами,
однако возможности и компромиссы нужно оценивать по конкретному продукту.

Гибкая документная схема позволяет хранить записи разной структуры,
но выбор БД должен опираться на запросы, согласованность, транзакции и эксплуатацию, а не на ярлык SQL/NoSQL.
</b></details>

<summary>Как с помощью WITH показать покупателей кошачьего корма и сумму их покупок корма?</summary><br><b>

From Orders <br>

) <br>
Select Customer_name, TOTAL_PRICE <br>

Здесь сначала рассчитывается сумма покупок корма по каждому Customer_ID,

</summary><br><b>

  * Glance — сервис образов, участвующий в хранении образов снимков экземпляров.
  * Horizon — веб-интерфейс управления ресурсами.
  * Cinder — блочное хранилище.
  * Nova — управление виртуальными экземплярами.
</b></details>

<details>
<summary>Что такое tenant/project?</summary><br><b>
Проект, ранее tenant, — единица владения и изоляции ресурсов OpenStack: ВМ, томов и сетей. Доступ пользователей определяется назначенными ролями; ресурсы разных проектов по умолчанию разделены, если явно не предоставлен общий доступ.
</b></details>

<details>
<summary>Определите, верны ли утверждения:

  * OpenStack можно использовать бесплатно.
  * За сеть отвечает Glance.
  * Основная цель проекта — совместное использование ресурсов разных проектов.</summary><br><b>
  * Бесплатное использование — **верно** для открытого ПО OpenStack; эксплуатация и коммерческая поддержка могут стоить денег.
  * Сеть обслуживает Glance — **неверно**: это Neutron, а Glance отвечает за образы.
  * Главная цель проекта — совместное использование — **неверно**: прежде всего это изоляция и управление ресурсами.
</b></details>

<details>
<summary>Как запустить экземпляр с floating IP?</summary><br><b>
Основные шаги:
1. Создать приватную сеть и подсеть.
2. Создать маршрутизатор, подключить приватную подсеть и внешний шлюз.
3. Запустить экземпляр в приватной сети и получить внутренний адрес.
4. Выделить проекту floating IP из внешнего пула.
5. Связать его с портом экземпляра и разрешить нужный трафик. Доступность из интернета зависит также от маршрутизации внешней сети.
</b></details>

<details>
<summary>Клиент может выполнить ping экземпляра, но не подключиться по SSH. Почему?</summary><br><b>
Возможные причины:
* Группа безопасности не разрешает TCP на порт SSH, обычно 22.
* Локальный firewall, например `iptables` или `firewalld`, блокирует соединение.
* `sshd` не запущен или неправильно настроен.
* Неверные имя пользователя или закрытый ключ, если соединение устанавливается, но аутентификация не проходит.
</b></details>

<details>
<summary>Какие типы сетей поддерживает OpenStack?</summary><br><b>
В зависимости от плагинов Neutron поддерживает:
* Local: сеть в пределах одного вычислительного узла.
* Flat: физическая сеть без VLAN-тегов.
* VLAN: изоляция канальных доменов с помощью 802.1Q.
* VXLAN: инкапсуляция Ethernet в UDP для множества логических сетей.
* GRE: туннелирование для построения оверлейных сетей.
</b></details>

<details>
<summary>Как диагностировать проблемы хранения OpenStack?</summary><br><b>
Для Cinder можно проверить:
* Журналы, например `/var/log/cinder/cinder-volume.log` и `/var/log/cinder/cinder-api.log`.
* Статусы томов, снимков, сервисов и backend через CLI; в исходнике указан `cinder`, также применяется клиент `openstack`.
* Согласованность состояния и метаданных БД, не внося неподтверждённых ручных изменений.
* Состояние и журналы самого хранилища: LVM, Ceph, NFS и т. д.
</b></details>

<details>
<summary>Как диагностировать вычислительные проблемы OpenStack?</summary><br><b>
Для Nova проверьте:
* Журналы `nova-compute`, `nova-api`, `nova-scheduler`, например в `/var/log/nova/`.
* Статус экземпляров, хостов и сервисов через CLI Nova/OpenStack.
* Консольный журнал экземпляра, включая сообщения загрузки.
* Состояние гипервизора и журналы KVM/QEMU или используемой платформы.
</b></details>

<a id="openstack-networking-neutron"></a>
#### Сети OpenStack: Neutron

<details>
<summary>Подробно опишите Neutron.</summary><br><b>

* Один из основных проектов OpenStack.
* Предоставляет сеть как сервис.
* Позволяет создавать сети и настраивать сетевые функции облака.
* Взаимодействует с:
  * Keystone для проверки доступа к API.
  * Nova для подключения интерфейсов экземпляров.
  * Horizon для управления сетью и отображения топологии.
</b></details>

<details>
<summary>Объясните назначение компонентов:

  - neutron-dhcp-agent
  - neutron-l3-agent
  - neutron-metering-agent
  - neutron-*-agtent
  - neutron-server</summary><br><b>


* `neutron-l3-agent` — маршрутизация и NAT, например доступ ВМ во внешнюю сеть.
* `neutron-dhcp-agent` — DHCP.
* `neutron-metering-agent` — измерение L3-трафика.
* Агенты конкретного backend управляют локальным виртуальным коммутатором; в исходнике `agtent` — опечатка.
* `neutron-server` предоставляет API и передаёт операции плагинам.
</b></details>

<details>
<summary>Объясните назначение сетей:

  * Сеть управления (Management Network).
  * Гостевая сеть (Guest Network).
  * Сеть API.
  * Внешняя сеть (External Network).</summary><br><b>

* Management: внутреннее взаимодействие компонентов; доступ обычно ограничен инфраструктурой ЦОД.
* Guest: трафик экземпляров и проектов.
* API: доступ к API сервисов. Он может быть публичным или внутренним в зависимости от endpoint и архитектуры.
* External: связь с внешними сетями. Наличие внешней сети не означает открытого доступа из интернета к каждому адресу.
</b></details>

<details>
<summary>В каком порядке удалять следующие объекты?

  * Сеть.
  * Порт.
  * Маршрутизатор.
  * Подсеть.</summary><br><b>

  * Освободить и удалить порты, включая интерфейсы маршрутизатора.
  * Удалить подсеть после удаления зависимостей.
  * Удалить маршрутизатор после отключения интерфейсов и шлюза.
  * Удалить сеть.

Порядок определяется зависимостями: нельзя удалить ресурс, пока его используют другие. Например, сначала отключают интерфейсы маршрутизатора.
</b></details>

<details>
<summary>Что такое provider network?</summary><br><b>
Сеть, которую администратор сопоставляет физической сети ЦОД, обычно flat или VLAN. Она позволяет напрямую подключать экземпляры к соответствующему канальному сегменту.
</b></details>

<details>
<summary>Какие компоненты отвечают за L2 и L3?</summary><br><b>
* L2: например, `neutron-openvswitch-agent` управляет виртуальным коммутатором, подключениями и правилами. Состав зависит от backend; OVN использует другую архитектуру.
* L3: в агентной архитектуре `neutron-l3-agent` обеспечивает виртуальные маршрутизаторы, NAT и floating IP.
</b></details>

<details>
<summary>Что такое ML2 и как он устроен?</summary><br><b>
Modular Layer 2 позволяет сочетать разные сетевые технологии. Type drivers обслуживают типы сетей, например VLAN/VXLAN, а Mechanism drivers реализуют подключение к backend, например Open vSwitch или OVN.
</b></details>

<details>
<summary>Как работает L2-агент?</summary><br><b>
Получает сведения от Neutron и настраивает локальные порты и виртуальный коммутатор, чтобы экземпляры подключались к нужным сетям. Также участвует в применении правил безопасности в зависимости от backend.
</b></details>

<details>
<summary>Как работает L3-агент?</summary><br><b>
В соответствующей архитектуре управляет маршрутизаторами, сетевыми namespace, маршрутами и NAT. Размещение на сетевых или вычислительных узлах зависит от централизованного или распределённого режима.
</b></details>

<details>
<summary>За что отвечает Metadata Agent?</summary><br><b>
Проксирует запросы метаданных экземпляров к Nova: идентификатор, имя, открытые ключи и другие сведения. Точное размещение и путь запроса зависят от сетевого backend.
</b></details>

<details>
<summary>Какие сетевые сущности предоставляет Neutron?</summary><br><b>
Основные сущности:
* Network — изолированный канальный домен.
* Subnet — диапазон IP и связанные параметры адресации.
* Port — точка подключения интерфейса устройства к сети.
* Router — маршрутизация между сетями.
* Floating IP — внешний адрес, сопоставляемый внутреннему адресу порта.
* Security Group — набор правил фильтрации трафика.
</b></details>

<details>
<summary>Как диагностировать сеть OpenStack?</summary><br><b>
Полезны следующие средства:
* Журналы Neutron, например `neutron-server.log`, `openvswitch-agent.log`, `l3-agent.log` в `/var/log/neutron/`.
* CLI OpenStack/Neutron для проверки сетей, подсетей, портов и маршрутизаторов.
* `ip netns` для просмотра изолированных сетевых стеков.
* `ovs-vsctl` и `ovs-ofctl` для конфигурации мостов и таблиц потоков OVS.
* `tcpdump` для отслеживания пакетов на разных участках пути.
</b></details>

<a id="openstack---glance"></a>
#### OpenStack - Glance

<details>
<summary>Подробно опишите Glance.</summary><br><b>

* Сервис образов OpenStack.
* Обрабатывает регистрацию, получение и хранение образов дисков.
* Участвует в хранении образов, создаваемых из снимков экземпляров.
* Пользователи могут загружать и регистрировать образы.
</b></details>

<details>
<summary>Как устроен Glance?</summary><br><b>

* `glance-api` принимает запросы работы с образами. Описание отдельных registry API в исходнике относится к старой архитектуре.
* `glance-registry` исторически обслуживал метаданные и был внутренним компонентом; не следует считать его обязательным в современных версиях.
* Metadata Definitions API управляет определениями метаданных.
* БД хранит метаданные образов.
* Backend хранит содержимое: например, файловая система или Swift; возможности зависят от драйвера.
</b></details>

<a id="openstack---swift"></a>
#### OpenStack - Swift

<details>
<summary>Подробно опишите Swift.</summary><br><b>

* Распределённое высокодоступное объектное хранилище с моделью eventual consistency.
* Данные распределяются по серверам и дискам с резервированием.
* Добавление серверов увеличивает ёмкость, а механизмы сервиса поддерживают целостность и нужную избыточность данных.
</b></details>

<details>
<summary>Можно ли по умолчанию хранить объект размером 100 ГБ?</summary><br><b>

Обычный объект имеет ограничение размера, в исходнике указано 5 ГБ. Для больших логических объектов используются сегменты и механизмы large objects; настройки зависят от установки.
</b></details>

<details>
<summary>Что означают в Swift:

  * Контейнер.
  * Аккаунт.
  * Объект.
</summary><br><b>

  * Контейнер — пространство имён объектов.
  * Аккаунт — пространство имён контейнеров.
  * Объект — содержимое, например изображение или документ.
</b></details>

<details>
<summary>Верно ли, что одинаковые имена объектов допустимы в одном контейнере, но не в разных?</summary><br><b>

Неверно: одинаковые имена допустимы в разных контейнерах.
</b></details>

<a id="openstack-advanced---keystone"></a>
#### OpenStack: расширенные вопросы Keystone

<details>
<summary>Подробно опишите Keystone.</summary><br><b>

* Центральный сервис идентификации обычной установки OpenStack.
* Предоставляет идентификацию, токены, каталог и связанные интерфейсы управления доступом.
  * Аутентифицирует пользователей и сервисы.
  * Выдаёт токены с контекстом, который сервисы используют при авторизации.
* Политики RBAC определяют допустимые действия. Упоминание одного JSON-файла в исходнике упрощено: формат и расположение политик зависят от сервиса и версии.
</b></details>

<details>
<summary>Опишите архитектуру Keystone.</summary><br><b>

* Запросы поступают через API; разделение service/admin API в исходнике отражает историческую архитектуру.
* Среди подсистем:
  * Token — выдача и проверка временных токенов.
  * Policy — интерфейсы политик в соответствующей версии.
  * Identity — пользователи и группы, например в SQL или LDAP.
  * Catalog — каталог endpoints.
* В исходнике перечислены разные исторические способы интеграции и хранения; их поддержка зависит от компонента и версии:
    * LDAP
    * KVS — хранилище ключ–значение.
    * SQL
    * PAM
    * Memcached
</b></details>

<details>
<summary>Как проходит аутентификация Keystone?</summary><br><b>

* Клиент обращается к auth URL с учётными данными и нужным контекстом доступа.
* После успешной проверки получает токен.
* Затем предъявляет токен сервисам вместо повторной передачи пароля. Токен не обязательно содержит список всех проектов пользователя; scope задаёт область конкретного доступа.
</b></details>

<a id="openstack-advanced---compute-nova"></a>
#### OpenStack: расширенные вопросы Nova

<details>
<summary>За что отвечают следующие компоненты?

  * nova-api
  * nova-compute
  * nova-conductor
  * nova-cert
  * nova-consoleauth
  * nova-scheduler
</summary><br><b>

  * `nova-api` — обработка запросов.

</b></details>

<details>

</b></details>

</b></details>

<a id="puppet"></a>
## Puppet

<details>
<summary>Что такое Puppet и как он работает?</summary><br><b>

* Средство управления конфигурацией, приводящее системы к описанному желаемому состоянию.
</b></details>
<details>
<summary>Опишите архитектуру Puppet.</summary><br><b>

* В типичной схеме агент–сервер агенты передают факты серверу, тот компилирует каталог желаемого состояния, а агенты применяют его. Для доверенной связи используются сертификаты: агент отправляет запрос, центр сертификации подписывает его согласно политике. Автоматическое подписание не обязательно включено.
</b></details>

<details>
<summary>Сравните Puppet с другими средствами управления конфигурацией. Почему вы выбрали его?</summary><br><b>

* Сравнивать можно с Chef, Ansible, Salt и CFEngine. Выбор зависит от модели управления, масштаба, опыта команды, экосистемы и требований эксплуатации.
</b></details>

<details>
<summary>Объясните следующие понятия:

  * Модуль.
  * Манифест.
  * Узел.
</summary><br><b>
  
* Модуль — набор манифестов, шаблонов, файлов и других компонентов.
* Манифест — код описания конфигурации ресурсов.
* Объявление узла позволяет назначить конфигурацию конкретным узлам.
</b></details>

<details>
<summary>Что такое Facter?</summary><br><b>

* Инструмент сбора фактов о системе: ОС, адреса, память, интерфейсы и другие свойства. Puppet использует их при формировании конфигурации с учётом особенностей узла.
</b></details>

<details>
<summary>Что такое MCollective?</summary><br><b>

* Исторический инструмент распределённого удалённого выполнения и оркестрации, интегрировавшийся с Puppet.
</b></details>

<details>
<summary>Писали ли вы модули Puppet? Для каких задач?</summary><br><b>

Ответьте по настоящему опыту: какие ресурсы описывал модуль, как использовал facts и Hiera, что делал при повторном применении и как тестировался. Если опыта нет, опишите план небольшого модуля без утверждения о выполненной работе.
</b></details>

<details>
<summary>Что такое Hiera?</summary><br><b>

* Иерархическая система поиска данных конфигурации Puppet, отделяющая значения от кода для удобства управления и повторного использования.
</b></details>

<a id="elastic"></a>
## Elastic

<details>
<summary>Что входит в Elastic Stack?</summary><br><b>

В исходнике перечислены:

  * Elasticsearch
  * Kibana
  * Logstash
  * Beats
  * Elastic Hadoop
  * APM Server

Elasticsearch, Logstash и Kibana также называют ELK.
</b></details>

<details>
<summary>Что такое Elasticsearch?</summary><br><b>

Согласно официальной [документации](https://www.elastic.co/guide/en/elasticsearch/reference/current/documents-indices.html):

Это распределённая система поиска и хранения документов. Данные представлены JSON-документами со структурированными полями, а не только строками реляционных таблиц.
</b></details>

<details>
<summary>Что такое Logstash?</summary><br><b>
	
Согласно [статье](https://logit.io/blog/post/the-top-50-elk-stack-and-elasticsearch-interview-questions):

Это конвейер сбора, преобразования, обогащения и передачи данных, часто используемый для обработки журналов.
</b></details>

<details>
<summary>Что такое Beats?</summary><br><b>

Лёгкие агенты доставки данных, устанавливаемые рядом с их источником.
Примеры: Filebeat, Metricbeat, Auditbeat.<br>
</b></details>

<details>
<summary>Что такое Kibana?</summary><br><b>

В документации она описывается как:

Платформа исследования и визуализации данных Elasticsearch. Позволяет искать документы, анализировать показатели и строить графики, таблицы и карты. Условия лицензирования следует проверять для выбранной версии.
</b></details>

<details>
<summary>Как запись журнала приложения попадает на панель Elastic Stack?</summary><br><b>

Путь зависит от архитектуры. Один из вариантов:

1. Filebeat читает журнал и передаёт данные в Logstash.
2. Logstash применяет фильтры и отправляет результат в Elasticsearch.
3. Elasticsearch сохраняет и индексирует документ.
4. Пользователь создаёт визуализации в Kibana по этим данным.
5. Объединяет визуализации в панель.
</b></details>

<a id="elasticsearch"></a>
##### Elasticsearch

<details>
<summary>Что такое data node?</summary><br><b>

Узел, хранящий шарды и выполняющий операции с данными, например поиск и индексацию.
</b></details>

<details>
<summary>Что такое master node?</summary><br><b>

Избранный управляющий узел отвечает, в частности, за:
* Состав и состояние кластера.
* Управление размещением шардов и реплик.
* Решения о распределении шардов; это не гарантирует автоматического устранения любой неравномерной нагрузки.

Master-eligible узлов может быть несколько, но в устойчивом состоянии активный избранный master один.
</b></details>

<details>
<summary>Что такое ingest node?</summary><br><b>

Узел, выполняющий ingest pipeline — обработку документа перед индексированием.
В некоторых архитектурах данные от Beats можно обрабатывать таким конвейером,
не используя Logstash; набор возможностей у них различается.
</b></details>

<details>
<summary>Что такое coordinating-only node?</summary><br><b>

В документации она описывается как:

Узел без других специализированных ролей, который принимает запросы, распределяет их по нужным шардам и объединяет результаты. Он получает состояние кластера и может разгружать data- и master-eligible узлы.

</b></details>

<details>
<summary>Как хранятся данные Elasticsearch?</summary><br><b>

* Документы объединяются в индексы.
* Индексы разделяются на шарды, размещённые на узлах кластера.
</b></details>

<details>
<summary>Что такое индекс?</summary><br><b>

Логическая коллекция документов с общими настройками и mapping. Сравнение с целой SQL-БД лишь приблизительное.<br>
Можно создать один индекс для приложения или несколько, например по сервисам или типам данных, учитывая объём и схему запросов.

Определение из документации:

Индекс — оптимизированная коллекция документов; документ состоит из полей, содержащих данные в виде пар ключ–значение.
</b></details>

<details>
<summary>Что такое шарды?</summary><br><b>

Индекс разбивается на самостоятельные части на базе Lucene. Документ направляется в шард по routing, обычно на основе идентификатора; шарды могут размещаться на разных узлах.<br>
Это позволяет распределять хранение и обработку по кластеру.
</b></details>

<details>
<summary>Что такое инвертированный индекс?</summary><br><b>

В документации она описывается как:

Структура, сопоставляющая термины спискам документов, в которых они встречаются.
</b></details>

<details>
<summary>Что такое документ?</summary><br><b>

Единица данных, приблизительно соответствующая строке SQL-таблицы или документу NoSQL-коллекции.
Это JSON-объект с полями сущности приложения, например книги или товара.
</b></details>

<details>
<summary>Что означают красный, жёлтый и зелёный статусы кластера?</summary><br><b>

Красный: не назначен хотя бы один primary shard, часть данных недоступна.
Другие состояния:
Жёлтый: все primary назначены, но отсутствуют некоторые реплики. Такое бывает на одном узле при настроенных репликах.
Зелёный: все основные и репликационные шарды назначены. Это не исключает проблем производительности.
</b></details>

<details>
<summary>Верно ли, что Elasticsearch индексирует каждое поле одинаковой структурой?</summary><br><b>

Неверно.
В документации она описывается как:

Нет. Структура зависит от типа поля: например, инвертированные индексы для текста и BKD-деревья для некоторых числовых и географических данных. Индексирование отдельных полей можно отключить.
</b></details>

<details>
<summary>Какие служебные поля документа вы знаете?</summary><br><b>

  * _index
  * _id
  * `_type` — историческое поле; типы mapping удалены из современных версий.
</b></details>

<details>
<summary>Что такое mapping?</summary><br><b>

Схема типов и настроек полей индекса Elasticsearch. Явный mapping предотвращает нежелательное автоматическое определение типов и позволяет выбрать text/keyword, анализаторы и форматы дат. Изменить тип существующего заполненного поля обычно нельзя без нового индекса и reindex.
</b></details>

<details>
<summary>Зачем задавать mapping явно?</summary><br><b>

* Настроить поля для частичного совпадения.
* Указать форматы, например даты.
* Настроить анализ текста для нужного языка.
</b></details>

<details>
<summary>Что такое реплики?</summary><br><b>

При отказе узла или шарда требуется сохранение доступа к данным.
Реплика — дополнительная копия primary shard на другом узле. Она помогает отказоустойчивости и обслуживанию чтений.
</b></details>

<details>
<summary>Что такое Term Frequency и Document Frequency?</summary><br><b>

TF — частота термина внутри документа, DF — число документов, в которых термин встречается. Они участвуют в моделях релевантности; простой формулы TF/DF, приведённой в исходнике, недостаточно для описания реального ранжирования.
</b></details>

<details>
<summary>Что означает фаза hot в Index Lifecycle Management?</summary><br><b>

Фаза активной записи и частых обращений к индексу.
Подробнее о фазах — [здесь](https://www.elastic.co/guide/en/elasticsearch/reference/7.6/ilm-policy-definition.html).
</b></details>

<details>
<summary>Что делает команда <code>curl -X PUT "localhost:9200/customer/_doc/1?pretty" -H 'Content-Type: application/json' -d'{ "name": "John Doe" }'</code>?</summary><br><b>

Записывает документ с явно заданным ID `1` и полем `name`, равным `John Doe`, в индекс `customer`. Если индекс отсутствует, он создастся при разрешённом автоматическом создании.
</b></details>

<details>
<summary>Что произойдёт при повторном выполнении команды два или сто раз?</summary><br><b>

1. Документ с ID `1` будет заменён указанным содержимым, а не добавлен под новым ID.
2. Для такой операции индексирования версия документа увеличивается.
</b></details>

<details>
<summary>Что такое Bulk API и зачем он нужен?</summary><br><b>

Позволяет выполнять несколько операций с документами одним запросом, сокращая сетевые накладные расходы по сравнению с отдельными запросами.
</b></details>

<a id="query-dsl"></a>
##### Query DSL

<details>
<summary>Объясните синтаксис запросов Elasticsearch: логические условия, поля и диапазоны.</summary><br><b>

Query DSL использует JSON: bool объединяет must/should/filter/must_not; term подходит для точного значения, match — для анализируемого текста, range — для границ. Выбор зависит от mapping. Не подставляйте пользовательский ввод в произвольную строку запроса без проверки.
</b></details>

<details>
<summary>Что такое оценка релевантности?</summary><br><b>

Число, показывающее соответствие документа поисковому запросу в query context. Зависит от запроса и статистики, обычно с использованием BM25 для текста. Это не процент вероятности и не сопоставимая абсолютная величина между любыми запросами; фильтры могут вообще не вычислять score.
</b></details>

<details>
<summary>Чем Query Context отличается от Filter Context?</summary><br><b>

В документации она описывается как:

В query context условие проверяет совпадение и оценивает, насколько документ соответствует запросу; результат отражается в `_score`.

В filter context проверяется только соответствие условию, без вычисления релевантности. Это удобно для точных ограничений по структурированным данным.
</b></details>

<details>
<summary>Чем крупная production-архитектура Elastic отличается от небольшой установки?</summary><br><b>

Возможный ответ:

Небольшая установка может состоять из Beats, Logstash, Elasticsearch и Kibana без дополнительных промежуточных сервисов.<br>
При больших объёмах нужны планирование шардов и ролей, отказоустойчивость и управление потоком; иногда добавляют буфер или очередь, например Redis/RabbitMQ, и прокси для контроля доступа. Они не заменяют встроенные механизмы защиты.
</b></details>

<a id="logstash"></a>
##### Logstash

<details>
<summary>Какие типы плагинов есть в Logstash?</summary><br><b>

* Input — приём данных из источников.
* Filter — преобразование и обогащение.
* Output — отправка в целевые системы.
</b></details>

<details>
<summary>Что такое grok?</summary><br><b>

Фильтр Logstash для разбора неструктурированного текста в поля с помощью именованных шаблонов регулярных выражений.
</b></details>

<details>
<summary>Как работает grok?</summary><br><b>

Сопоставляет текст именованным regex-шаблонам, извлекая поля, например `%{IP:client_ip}`. Важно ограничивать шаблоны, обрабатывать несовпадение и не допускать дорогого backtracking. Для уже структурированного JSON лучше соответствующий parser.
</b></details>

<details>
<summary>Какие grok-шаблоны вы знаете?</summary><br><b>

Например, IP, NUMBER, WORD, NOTSPACE, TIMESTAMP_ISO8601, HTTPDATE. Проверьте набор паттернов установленной версии и ожидаемый формат, а не считайте название универсальной проверкой любых значений.
</b></details>

<details>
<summary>Что означает `_grokparsefailure`?</summary><br><b>

Стандартный тег при неудаче разбора grok, если tag_on_failure не переопределён. Разделите такие события в диагностический поток и уточните шаблон; молча удалять все неразобранные журналы опасно для наблюдаемости.
</b></details>

<details>
<summary>Как проверять и отлаживать grok-шаблоны?</summary><br><b>

Проверяйте на наборе реальных обезличенных строк, включая крайние случаи и несовпадения, через Grok Debugger или тестовый pipeline. Сопоставляйте итоговые поля и типы, измеряйте производительность и ограничивайте длительность regex. Не отправляйте секретные журналы в публичные отладчики.
</b></details>

<details>
<summary>Что такое codecs в Logstash? Какие примеры вы знаете?</summary><br><b>

Кодеки преобразуют данные на входе/выходе, например plain, json, json_lines и multiline. Multiline нужно применять там, где сохраняется принадлежность строк одному источнику; смешивание потоков может склеить разные события.
</b></details>

<a id="kibana"></a>
##### Kibana

<details>
<summary>Что показывает Discover в Kibana?</summary><br><b>

Документы выбранного представления данных; их можно искать, фильтровать и просматривать.
</b></details>

<details>
<summary>Что означает «561 hits» в Discover?</summary><br><b>

Число документов, соответствующих запросу, фильтрам и выбранному временному диапазону.
</b></details>

<details>
<summary>Для чего нужен раздел Visualize?</summary><br><b>

Для создания графиков, диаграмм и других визуализаций данных.
</b></details>

<details>
<summary>Какие типы визуализаций поддерживает Kibana?</summary><br><b>

Например, временные ряды, столбцы, круговые диаграммы, таблицы, карты и метрики; инструменты и названия разделов зависят от версии Kibana. Выбирайте визуализацию по вопросу к данным, учитывая фильтры и диапазон времени.
</b></details>

<details>
<summary>Какую визуализацию выбрать для поиска статистических выбросов?</summary><br><b>

<a id="distributed"></a>
## Распределённые системы

<details>
<summary>Что такое распределённая система?</summary><br><b>

В формулировке Мартина Клеппмана:

Множество процессов на разных машинах взаимодействует сообщениями через сеть с переменной задержкой. Возможны частичные отказы, неточные часы и паузы процессов.

Иначе говоря, физически разделённые компоненты работают как логически связанная система.
</b></details>

<details>
<summary>Что может вызвать отказ системы?</summary><br><b>

* Сеть.
* Процессор.
* Память.
* Диск.
</b></details>

<details>
<summary>Что утверждает теорема CAP, или теорема Брюера?</summary><br><b>

При сетевом разделении невозможно одновременно гарантировать линейризуемую согласованность и доступность в смысле CAP. Формула «выберите любые два из трёх» в исходнике чрезмерно упрощает утверждение.

* Availability: каждый запрос к исправному узлу получает завершённый ответ согласно модели, без требования обязательно возвращать новейшие данные.
* Consistency: операции выглядят как работа с одной актуальной копией, с соблюдением порядка реального времени.
* Partition tolerance: система рассматривается при потере связи между частями сети, а не просто при утрате произвольных данных.
</b></details>

<details>
<summary>Какие проблемы есть в этой схеме? Как её улучшить?<br>
<img src="images/distributed/distributed_design_standby.png" width="500x;" height="350px;"/>
</summary><br><b>
1. Переключение может занять время и вызвать заметный простой.
2. Резервный сервер может простаивать, хотя это осознанная плата за резервирование, а не всегда ошибка.
</b></details>

<details>
<summary>Какие проблемы есть в этой схеме? Как её улучшить?<br>
<img src="images/distributed/distributed_design_lb.png" width="700x;" height="350px;"/>
</summary><br><b>
Проблемы:
При отказе единственного балансировщика приложение станет недоступно.

Варианты улучшения:
* Добавить резервный балансировщик.
* Настроить механизм переключения; несколько DNS A-записей сами по себе не гарантируют быстрый failover.
* Для подходящих асинхронных операций использовать очередь; она не заменяет резервирование входной точки.
</b></details>

<details>
<summary>Что такое архитектура Shared-Nothing?</summary><br><b>

Каждый узел использует собственные память и хранилище, а данные и работа распределены между узлами. В отличие от shared-storage, общего диска или памяти нет; координация идёт по сети.
</b></details>

<details>
<summary>Объясните паттерн Sidecar, в том числе sidecar proxy.</summary><br><b>

Вспомогательный компонент развёртывается рядом с приложением и обслуживает общую функцию: прокси, сбор логов, обновление конфигурации. В Kubernetes sidecar может жить в том же Pod. Это добавляет ресурсные затраты и вопросы старта/остановки; локальное соседство не отменяет настройки безопасности.
</b></details>

#### API

<details>
<summary>Что такое API?</summary><br><b>

<details>

<details>
<summary>Что такое API Gateway?</summary><br><b>

Входной компонент, принимающий клиентские API-запросы и передающий их внутренним сервисам.

Может выполнять маршрутизацию, балансировку, аутентификацию, ограничение частоты, кэширование и сбор метрик.

Позволяет централизовать общие правила доступа и упростить клиентам работу с множеством микросервисов. Его собственную ёмкость и отказоустойчивость нужно проектировать отдельно.
</b></details>

<details>
<summary>Каковы преимущества API Gateway?</summary><br><b>

Преимущества:

* Единая точка управления и наблюдения за API.
* Общие механизмы аутентификации, авторизации и защиты соединений.
* Управление потоком запросов и распределение нагрузки.
* Объединение нескольких внутренних операций в удобный внешний API.
* Контролируемая публикация внутренних сервисов партнёрам и клиентам.

</b></details>

<details>
<summary>Что такое payload API-запроса?</summary><br><b>

Полезная часть передаваемых данных, обычно тело запроса/ответа, а не служебные заголовки. Её формат задаёт Content-Type и контракт API; проверяйте размер, схему, типы и семантику, а не только корректность JSON.
</b></details>

<details>
<summary>Чем автоматизация отличается от оркестрации?</summary><br><b>

Автоматизация уменьшает ручное участие в выполнении отдельных задач.<br>
Оркестрация согласует последовательность и зависимости нескольких автоматизированных задач, часто между разными системами.
</b></details>

<details>
<summary>Расскажите об интересных ошибках, которые вы нашли и исправили.</summary><br><b>

Приведите реальный случай: симптом, влияние, гипотезы, доказательства, исправление и проверка отсутствия регрессии. Отделите свой вклад от работы команды и объясните, что предотвратит повторение. При отсутствии опыта допустимо рассказать о воспроизводимой учебной ошибке как об учебной.
</b></details>

<details>
<summary>Что такое отладчик и как он работает?</summary><br><b>

Средство управления исполнением и исследования состояния: breakpoints, шаги, стек, переменные, регистры и память. Может подключаться к работающему процессу или читать core dump; символы отладки помогают. Остановка процесса и просмотр памяти требуют учёта производственного влияния и секретов.
</b></details>

Данные, описывающие другие данные: например, формат, автора, размер или время создания.
</b></details>

<details>

<a id="http"></a>
## HTTP

<details>
<summary>Что такое HTTP?</summary><br><b>

[Avinetworks](https://avinetworks.com/glossary/layer-7/): Hypertext Transfer Protocol — прикладной протокол передачи ресурсов. Обычный HTTP использует порт 80; HTTP/1.1 и HTTP/2 работают поверх TCP, HTTP/3 — поверх QUIC.
</b></details>

<details>
<summary>Опишите жизненный цикл HTTP-запроса.</summary><br><b>

* Разрешение имени через DNS при необходимости.
* Для нового TCP-соединения клиент отправляет SYN.
* Сервер отвечает SYN/ACK, клиент — ACK; для HTTPS затем требуется TLS. В исходнике ACK пропущен.
* Для нового TCP-соединения клиент отправляет SYN.
* Отправка HTTP-запроса.
* Получение HTTP-ответа.
</b></details>

<details>
<summary>Верно ли, что HTTP сам хранит состояние между запросами?</summary><br><b>

Нет. HTTP stateless; сеансы приложения реализуются дополнительными механизмами, например cookie и хранилищем состояния.
</b></details>

<details>
<summary>Как выглядит HTTP-запрос?</summary><br><b>

В текстовом HTTP/1.1 он включает:

* Строку запроса с методом, целью и версией протокола.
* Заголовки, например тип и длину содержимого.
* Необязательное тело после пустой строки.
</b></details>

<details>
<summary>Какие HTTP-методы вы знаете?</summary><br><b>

* GET
* POST
* HEAD
* PUT
* DELETE
* CONNECT
* OPTIONS
* TRACE
</b></details>

<details>
<summary>Какие группы кодов ответа HTTP существуют?</summary><br><b>

* 1xx — информационные.
* 2xx — успешная обработка.
* 3xx — перенаправления.
* 4xx — ошибки запроса или доступа со стороны клиента.
* 5xx — ошибки обработки на стороне сервера.
</b></details>

<details>
<summary>Что такое HTTPS?</summary><br><b>


HTTP поверх TLS. Защищает передачу от чтения и изменения посредником и позволяет проверить подлинность сервера по сертификату.

Подробнее: https://www.cloudflare.com/learning/ssl/why-is-http-not-secure/
</b></details>

<details>
<summary>Что такое HTTP cookie?</summary><br><b>

HTTP не хранит состояние между запросами; cookie позволяют связывать запросы с состоянием приложения.

Cookie — небольшой набор данных, который браузер хранит и отправляет серверу по правилам домена, пути, срока действия и атрибутов защиты.
</b></details>

<details>
<summary>Что такое HTTP pipelining?</summary><br><b>

В HTTP/1.1 несколько запросов отправляются в одном соединении без ожидания ответа на каждый; ответы должны сохранять порядок, что создаёт head-of-line blocking. Это отличается от мультиплексирования HTTP/2. Не считайте pipelining повсеместно используемым браузерным механизмом.
</b></details>

<details>
<summary>Что означает 504 Gateway Timeout?</summary><br><b>

Шлюз или прокси не дождался своевременного ответа от вышестоящего сервера.
</b></details>

<details>
<summary>Что такое прокси?</summary><br><b>

Посредник между клиентом и сервером. В зависимости от типа и настройки может кэшировать ответы, фильтровать содержимое и скрывать адрес клиента от целевого сервера.
* Прокси также применяют для балансировки, журналирования и анализа трафика; эти возможности зависят от конкретного решения.
</b></details>

<details>
<summary>Что такое reverse proxy?</summary><br><b>

Обратный прокси представляет серверную сторону: клиент обращается к нему как к сервису, а он передаёт запрос внутреннему серверу. В отличие от forward proxy, он работает от имени обслуживаемых серверов, а не клиента.
* Используется для распределения запросов, TLS, кэширования и ограничения прямого доступа к backend. Может помогать масштабированию и отказоустойчивости при правильном резервировании.
</b></details>

<details>
<summary>Какие лицензии вы знаете? Какую выбрали бы для публикуемого проекта и почему?</summary><br><b>

Например, MIT, BSD, Apache-2.0, GPL и лицензии Creative Commons для подходящего контента. Выбор зависит от целей распространения, обязанностей и лицензий зависимостей. Не приписывайте себе права на чужой код; спорные условия требует разбирать по тексту лицензии и требованиям проекта.
</b></details>

<details>
<summary>Что такое X-Forwarded-For?</summary><br><b>

[Wikipedia](https://en.wikipedia.org/wiki/X-Forwarded-For): HTTP-заголовок для передачи исходного IP клиента через прокси или балансировщик. Доверять ему следует только с учётом доверенных прокси, иначе клиент может подделать значение.
</b></details>

<a id="load-balancers"></a>
#### Балансировщики нагрузки

<details>
<summary>Что такое балансировщик нагрузки?</summary><br><b>

Компонент, распределяющий входящие соединения или запросы между серверами по заданным правилам.
</b></details>

<details>
<summary>Зачем нужен балансировщик?</summary><br><b>

* Масштабирование: можно добавлять backend-серверы для обработки большей нагрузки.
* Отказоустойчивость: при неисправности цели новые запросы направляются исправным. Сохранение уже начатых запросов и сеансов требует дополнительных мер.
</b></details>

<details>
<summary>Какие алгоритмы балансировки вы знаете?</summary><br><b>

* Round Robin — по очереди.
* Weighted Round Robin — по очереди с весами.
* Least Connections — по наименьшему числу соединений.
* Weighted Least Connections — то же с весами.
* По доступным ресурсам.
* По фиксированным весам.
* По взвешенному времени ответа.
* По хешу IP источника.
* По хешу URL.
</b></details>

<details>
<summary>Каковы недостатки Round Robin?</summary><br><b>

* Не учитывает текущую нагрузку и различия серверов. Несколько тяжёлых запросов могут попасть на один сервер, хотя остальные заняты лёгкими.
* Последовательные запросы клиента могут попасть на разные серверы. Если состояние сеанса хранится только локально, это вызывает ошибки; алгоритм сам по себе не создаёт новый сеанс приложения на каждый запрос.
</b></details>

<details>
<summary>Что такое балансировщик прикладного уровня?</summary><br><b>

Балансировщик, понимающий прикладной протокол, например HTTP: может выбирать backend по host/path/headers и завершать TLS. Это даёт гибкость, но добавляет стоимость обработки и требует правильного доверия к forwarded-заголовкам.
</b></details>

<details>
<summary>Когда вы использовали бы ALB?</summary><br><b>

Для HTTP(S)-маршрутизации по host/path, нескольких веб-приложений и нужных L7-функций. Для произвольного TCP/UDP, статических IP и специфических требований может подойти L4-балансировщик. Уточняйте продукт: ALB может означать сервис конкретного облака.
</b></details>

<details>
<summary>На каких уровнях могут работать балансировщики?</summary><br><b>

Например, L4 и L7.
</b></details>

<details>
<summary>Можно ли распределять нагрузку без отдельного экземпляра балансировщика?</summary><br><b>

Да, например через DNS или клиентскую балансировку, с учётом их ограничений.
</b></details>

<details>
<summary>Что такое DNS-балансировка, каковы её преимущества и когда её использовать?</summary><br><b>

DNS возвращает разные адреса по политике: несколько значений, веса, география, задержка, состояние. Это удобно для геораспределения, но кэши и клиентский выбор ограничивают точность и скорость переключения. DNS не видит каждое HTTP-соединение и не заменяет балансировщик всех задач.
</b></details>

<a id="load-balancers---sticky-sessions"></a>
#### Балансировщики: привязка сеансов

<details>
<summary>Что такое sticky sessions? Каковы плюсы и минусы?</summary><br><b>

Дополнительное чтение:
* [Статья Red Hat](https://access.redhat.com/solutions/900933).

Недостатки:
* Может приводить к неравномерной нагрузке из-за привязки клиентов к серверам.
Преимущества:
* Позволяет повторно использовать состояние сеанса в памяти того же сервера, пока сервер доступен и привязка действует.
</b></details>

<details>
<summary>Приведите пример применения sticky sessions.</summary><br><b>

Сохранение доступа к локальному состоянию пользовательского сеанса при следующих запросах.
</b></details>

<details>
<summary>Что может обеспечивать привязку сеансов?</summary><br><b>

Например, cookie приложения или cookie балансировщика с заданным сроком действия.
</b></details>

<details>
<summary>Что такое привязка по cookie приложения?</summary><br><b>

* Использует cookie приложения, иногда вместе со служебной cookie балансировщика.
* Приложение управляет соответствующим значением и сроком сеанса; конкретные возможности зависят от балансировщика.
</b></details>

<details>
<summary>Что такое привязка по cookie с заданной длительностью?</summary><br><b>

* Cookie создаёт балансировщик.
* После истечения срока прежняя привязка перестаёт действовать.
</b></details>

<a id="load-balancers---load-balancing-algorithms"></a>
#### Алгоритмы балансировки

<details>
<summary>Объясните следующие алгоритмы балансировки:

* Round Robin — по очереди.
* Weighted Round Robin — по очереди с весами.
* Least Connections — по наименьшему числу соединений.
* Weighted Least Connections — то же с весами.
* По доступным ресурсам.
* По фиксированным весам.
* По взвешенному времени ответа.
* По хешу IP источника.
* По хешу URL.
</summary><br><b>

Round Robin выбирает по очереди; weighted — с долями по весам. Least Connections учитывает активные соединения, weighted учитывает ещё ёмкость. Resource/response-time policies используют поступающие показатели. Source-IP/URL hash закрепляют ключ за целью. Точная формула и поведение при отказах зависят от реализации; один долгий connection не равен одному дешёвому запросу.
</b></details>

<details>
<summary>Когда нужен connection draining?</summary><br><b>
При выводе сервера из обслуживания: новые запросы больше не направляются на него, а существующим дают завершиться в пределах тайм-аута. Детали поведения неисправных целей зависят от сервиса.

В исходнике указан диапазон 1–3600 секунд для AWS и GCP; точные ограничения следует проверять для выбранного балансировщика.

</b></details>

<a id="licenses"></a>
#### Лицензии

<details>
<summary>Что вы знаете о Creative Commons?</summary><br><b>

Семейство публичных лицензий, которыми автор задаёт условия использования и распространения произведения. Шесть основных вариантов:

* CC BY: распространение и переработка, включая коммерческие, с указанием автора.
* CC BY-SA: также требует распространять адаптации на тех же условиях лицензии.
* CC BY-ND: разрешает распространение без передачи переработанных версий, с указанием автора, в том числе коммерчески.
* CC BY-NC: разрешает некоммерческое использование и переработку с указанием автора.
* CC BY-NC-SA: некоммерческое использование, указание автора и те же условия для распространяемых адаптаций.
* CC BY-NC-ND: некоммерческое распространение без передачи адаптированных версий, с указанием автора.

Эти лицензии заранее определяют разрешённые способы использования. Подробные условия и исключения устанавливаются текстом конкретной лицензии.

Подробнее: https://creativecommons.org/licenses/
</b></details>

<details>
<summary>Чем copyleft-лицензии отличаются от разрешительных?</summary><br><b>

Copyleft требует сохранять установленные лицензионные условия при распространении охватываемых производных работ; конкретный охват зависит от лицензии. Разрешительные лицензии обычно не требуют лицензировать всю производную работу так же, но сохраняют требования, например уведомления об авторстве. Примеры: GPL-3.0 и BSD соответственно.
</b></details>

<a id="storage"></a>
## Хранение данных

<details>
<summary>Какие типы хранения данных существуют?</summary><br><b>

  * Файловое.
  * Блочное.
  * Объект.
</b></details>

<details>
<summary>Что такое объектное хранилище?</summary><br><b>

* Данные хранятся самостоятельными объектами с идентификаторами.
* Объект может содержать метаданные.
</b></details>

<details>
<summary>Каковы плюсы и минусы объектного хранения?</summary><br><b>

Преимущества:
* В облачных сервисах обычно оплачивается фактически хранимый объём и операции, а не заранее выделенный диск.
* Удобно масштабировать ёмкость по мере роста данных.
Недостатки:
* Задержки отдельных операций могут быть выше, чем у локального или блочного хранения; сравнение зависит от нагрузки.
* Обычно нельзя изменить произвольный участок объекта на месте: его заменяют целиком или используют специальные возможности сервиса.
</b></details>

<details>
<summary>Для каких задач подходит объектное хранилище?</summary><br><b>

Резервные копии, медиа, артефакты, статические ресурсы и наборы данных. Не заменяет автоматически POSIX-файловую систему или блочный том для БД; учитывайте модель объектов, операции, задержку, согласованность и стоимость извлечения.
</b></details>

<details>
<summary>Что такое файловое хранение?</summary><br><b>

* Данные организованы в файлы и иерархию каталогов.
* Файловая система может располагаться на локальном диске, флеш-накопителе или предоставляться по сети.
* Каталоги группируют файлы и другие каталоги.
</b></details>

<details>
<summary>Каковы особенности файлового хранения?</summary><br><b>

Преимущества:
* Поддерживает чтение, запись, удаление, переименование и перемещение файлов в пределах выданных прав.
* Предоставляет права доступа и, в зависимости от реализации, блокировки и другие средства совместной работы.
</b></details>

<details>
<summary>Приведите примеры файлового хранения.</summary><br><b>

Локальная файловая система.
Dropbox
Google Drive
</b></details>

<details>
<summary>Какие типы устройств хранения вы знаете?</summary><br><b>

HDD, SSD SATA/SAS/NVMe, ленты и оптические носители. NAS/SAN — способы предоставления доступа, а не отдельная физическая технология носителя. NVMe — протокол, SSD — тип устройства; эти категории нельзя сравнивать как взаимоисключающие.
</b></details>

<details>
<summary>Что такое IOPS?</summary><br><b>

Операции ввода-вывода в секунду. Значение имеет смысл вместе с размером блока, типом операции, случайностью доступа, глубиной очереди и задержкой. Сравнение IOPS разных тестов без одинаковых условий может быть бессмысленным.
</b></details>

<details>
<summary>Что такое throughput хранилища?</summary><br><b>

Объём переданных данных за единицу времени, например MiB/s. Примерно связан с IOPS × размер операции, но реальные результаты зависят от параллельности и нагрузки. Различайте MB и MiB, latency и throughput.
</b></details>

<details>
<summary>Что такое файловая система?</summary><br><b>

Правила и структуры для организации файлов, каталогов, метаданных и размещения данных на носителе или в виртуальном хранилище. Она позволяет находить данные и управлять ими по именам и путям.

Примеры файловых систем:
Windows:
  * NTFS
  * exFAT

macOS:
  * HFS+
  * APFS

</b></details>

<details>
<summary>Что такое Dark Data?</summary><br><b>

Собранные и сохраняемые данные, которые организация не использует для заявленной аналитической или операционной цели. Они могут создавать затраты и риски утечки; определите владельца, необходимость хранения, права и срок удаления.
</b></details>

<details>
<summary>Что такое MBR?</summary><br><b>

Master Boot Record — начальная структура диска с загрузочным кодом и классической таблицей разделов. Имеет ограничения, например для распространённого варианта с 512-байтными секторами около 2 TiB. GPT — более современная схема; BIOS/UEFI и MBR/GPT — связанные, но разные понятия.
</b></details>

<details>
<summary>Что такое тестирование белого ящика?</summary><br><b>

Проверка с использованием знания внутренней структуры: покрытие ветвей, путей и состояний, анализ зависимостей. Это подход к проектированию проверок, а не синоним только unit-тестов.
</b></details>

<details>
<summary>Что такое тестирование чёрного ящика?</summary><br><b>

Проверка входов и наблюдаемых выходов по контракту без опоры на внутреннюю реализацию. Включает границы, классы эквивалентности и ошибки. Может применяться на разных уровнях тестирования.
</b></details>

<details>
<summary>Что такое модульные тесты?</summary><br><b>

Автоматизированные проверки отдельных частей программы, обычно в изоляции от внешних зависимостей. Их регулярно запускают, чтобы быстро обнаруживать ошибки и регрессии.

Они проверяют ожидаемое поведение модуля при заданных условиях, включая граничные случаи.
</b></details>

<details>
<summary>Какими тестами вы проверяли бы веб-приложение?</summary><br><b>

Модульные и интеграционные проверки, API/контрактные, основные E2E-пути, права и безопасность, доступность интерфейса, совместимость браузеров и производительность по рискам. Набор выбирается по критичности, а не стремлению выполнить все виды на каждом коммите.
</b></details>

<details>
<summary>Что такое test harness?</summary><br><b>

Среда/код запуска проверок: подготовка данных и зависимостей, выполнение, сбор результатов и очистка. Должна воспроизводить нужные условия и не загрязнять следующие тесты.
</b></details>

<details>
<summary>Что такое A/B-тестирование?</summary><br><b>

Контролируемое сравнение вариантов на случайно распределённых группах. Заранее задайте метрику, достаточный объём, период и guardrails; проверяйте статистическую неопределённость и побочные эффекты. Это не просто попеременный показ двух страниц без контроля.
</b></details>

<details>
<summary>Что такое симуляция сети и как её выполнять?</summary><br><b>

Моделирование задержек, потерь и ограничений, например через Linux tc netem в изолированной тестовой среде. Важно знать направление воздействия и иметь консоль/откат. Не накладывайте ограничения на рабочий SSH-интерфейс без плана восстановления.
</b></details>

<details>
<summary>Какие виды тестирования производительности вы знаете?</summary><br><b>

Load, stress, spike, soak/endurance, объёмные и ёмкостные проверки. Для каждой задайте профиль нагрузки, длительность, latency/error/resource метрики и критерий успеха; среднее время ответа может скрывать плохие хвосты.
</b></details>

<details>
<summary>Объясните виды тестов:

  * Нагрузочное тестирование.
  * Стресс-тестирование.
  * Проверка предельной ёмкости.
  * Проверка с большими объёмами данных.
  * Длительное тестирование устойчивости.
</summary><br><b>

Load — ожидаемая нагрузка; stress — за пределами нормы и поведение отказа/восстановления; capacity — максимальная нагрузка при сохранении SLO; volume — большой объём данных; endurance — длительная работа для выявления утечек и деградации. Точные названия зависят от процесса команды.
</b></details>

<a id="regex"></a>
## Регулярные выражения

Выполните следующие задания для текстового файла.

<a id="extract"></a>
#### Извлечение

<details>
<summary>Извлеките все числа.</summary><br><b>

  - "\d+"
</b></details>

<details>
<summary>Извлеките первое слово каждой строки.</summary><br><b>

  - "^\w+"
Дополнительно: извлеките последнее слово каждой строки.

  - "\w+(?=\W*$)" — применимость зависит от формата строки и реализации regex.
</b></details>

<details>
<summary>Извлеките все IP-адреса.</summary><br><b>

  - Для кандидатов IPv4: `\b(?:\d{1,3}\.){3}\d{1,3}\b`. Это проверяет форму, но не диапазон 0–255 каждого октета; в исходнике перед точкой лишний пробел.
</b></details>

<details>
<summary>Извлеките даты формата yyyy-mm-dd или yyyy-dd-mm.</summary><br><b>

Для кандидатов используйте `\b[0-9]{4}-[0-9]{2}-[0-9]{2}\b`. Одно regex не различит yyyy-mm-dd и yyyy-dd-mm, если оба числовых поля не больше 12. После извлечения разберите календарной библиотекой по заранее заданному формату, проверяя дни и високосный год.
</b></details>

<details>
<summary>Извлеките адреса электронной почты.</summary><br><b>

  - Упрощённый шаблон: `\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}\b`. Он не покрывает весь стандарт адресов; лишний пробел исходника убран.
</b></details>

<a id="replace"></a>
#### Замена

<details>
<summary>Замените табуляции четырьмя пробелами.</summary><br><b>

Например, в Python: `text.replace(chr(9), ' ' * 4)`. Это замена каждой табуляции ровно четырьмя пробелами, а не выравнивание до tab stop; для последнего используют expandtabs/expand с другим результатом.
</b></details>

<details>
<summary>Замените 'red' на 'green'.</summary><br><b>

Точное вхождение подстроки в Python: `text.replace('red', 'green')`. Для отдельных слов — `re.sub(r'\bred\b', 'green', text)` после `import re`. Уточните регистр и правила границ слова; regex-движки различаются.
</b></details>

<a id="system-design"></a>
## Проектирование систем

<details>
<summary>Что такое единая точка отказа?</summary><br><b>
Компонент, отказ которого делает всю систему недоступной или существенно нарушает её работу,
поскольку другой компонент не может компенсировать его потерю.
</b></details>

<details>
<summary>Что такое CDN?</summary><br><b>

Content Delivery Network — географически распределённая сеть доставки контента. Пограничные узлы кэшируют данные ближе к пользователям, сокращая задержку и нагрузку на источник.
</b></details>

<details>
<summary>Что такое Multi-CDN?</summary><br><b>

При использовании одной CDN доставка зависит от одного провайдера CDN.<br>
Multi-CDN распределяет запросы между несколькими CDN, возможно разных провайдеров и облаков.
</b></details>

<details>
<summary>Каковы преимущества Multi-CDN?</summary><br><b>

* Устойчивость к отказу одного провайдера при корректном переключении. Одна CDN тоже имеет внутреннее резервирование.
* Возможность выбирать более выгодную доставку по регионам и условиям контрактов.
* Выбор лучшего пути и точки присутствия для конкретного пользователя.
* Дополнительная ёмкость для больших пиков нагрузки, ценой сложности управления.
</b></details>

<details>
<summary>Что такое трёхуровневая архитектура? Каковы её плюсы и минусы?</summary><br><b>
Приложение разделено на представление, бизнес-логику и хранение данных. Эти уровни взаимодействуют через определённые интерфейсы.
Плюсы:
* Независимое масштабирование уровней.
* Разделение доступа и функций безопасности.
* Повторное использование компонентов.
Минусы:
* Дополнительная сложность.
* Накладные расходы взаимодействия.
* Затраты на разработку и эксплуатацию.
</b></details>

<details>
<summary>Чем монорепозиторий отличается от нескольких репозиториев? Каковы компромиссы?</summary><br><b>
Монорепозиторий хранит код нескольких компонентов или проектов в одном репозитории.
Плюсы монорепозитория:
* Единые инструменты и правила.
* Удобное совместное изменение и использование кода.
Минусы:
* Сложность сборки, разграничения доступа и зависимостей при большом масштабе.
* Большой объём клонирования без специальных мер.

При нескольких репозиториях компоненты имеют отдельные истории и процессы выпуска.
Плюсы нескольких репозиториев:
* Проще изолировать управление отдельным компонентом.
* Команды могут независимо менять инструменты, доступ и цикл выпуска.
Минусы:
* Риск дублирования кода.
* Сложнее согласовывать изменения и версии между проектами.
</b></details>

<details>
<summary>Каковы возможные недостатки монолита?</summary><br><b>

* Общий цикл выпуска усложняет частые независимые изменения компонентов.
* Нельзя независимо масштабировать части без дополнительного разделения; при этом монолит вполне может работать в публичном облаке.
* Большой команде сложнее координировать изменения тесно связанного кода.
* Ошибка внутри общего процесса может затронуть всё приложение, хотя не любой отказ обязательно имеет такой эффект.
</b></details>

<details>
<summary>Какие преимущества могут дать микросервисы?</summary><br><b>

* Изоляция отказов отдельных сервисов при правильном проектировании зависимостей.
* Независимые команды, выпуски и выбор технологий, ценой распределённой сложности.
</b></details>

<details>
<summary>Что такое service mesh?</summary><br><b>
Инфраструктурный слой управления взаимодействием сервисов: маршрутизация, защищённые соединения, метрики и политики доступа. Не обязательно ограничивается только контейнерами.
</b></details>

<details>
<summary>Что такое слабая связанность?</summary><br><b>
Компоненты взаимодействуют через стабильные интерфейсы и мало зависят от внутренних деталей друг друга, поэтому их проще изменять независимо.
</b></details>

<details>
<summary>Что такое очередь сообщений и когда она нужна?</summary><br><b>
Механизм асинхронного обмена, отделяющий отправку работы от её обработки. Помогает сглаживать пики и развязывать компоненты; используется не только в микросервисах.
</b></details>

<a id="scalability"></a>
#### Масштабируемость

<details>
<summary>Что такое масштабируемость?</summary><br><b>

Способность увеличивать ёмкость системы при росте нагрузки с приемлемыми затратами и характеристиками работы.
</b></details>

<details>
<summary>Что такое эластичность?</summary><br><b>

Способность увеличивать и уменьшать выделенные ресурсы вслед за потребностью.
</b></details>

<details>
<summary>Что такое аварийное восстановление?</summary><br><b>


Восстановление критичных систем и данных после серьёзного сбоя. Включает план, резервные копии, независимые площадки и регулярные проверки восстановления. Цели RTO и RPO определяют допустимое время простоя и потерю данных; реальное восстановление может занять от минут до дней.
</b></details>

<details>
<summary>Чем отказоустойчивость отличается от высокой доступности?</summary><br><b>

Fault tolerance — способность продолжать корректную работу при предусмотренных отказах. Автоматическое восстановление помогает, но не исчерпывает понятие.

High availability — поддержание высокой доли времени доступности сервиса, обычно за счёт резервирования и быстрого переключения.
</b></details>

<details>
<summary>Чем высокая доступность отличается от аварийного восстановления?</summary><br><b>

[wintellect.com](https://www.wintellect.com/high-availability-vs-disaster-recovery): HA уменьшает вероятность и продолжительность отказов, устраняя единые точки отказа; DR возвращает систему в рабочее состояние после серьёзного нарушения, которое механизмы HA не смогли скрыть.
</b></details>

<details>
<summary>Что такое вертикальное масштабирование?</summary><br><b>

Увеличение ресурсов существующего узла: CPU, RAM, производительности хранения и т. д.
</b></details>

<details>
<summary>Каковы его недостатки?</summary><br><b>

Само увеличение сервера не устраняет единую точку отказа.
Также существуют аппаратные пределы и возможная необходимость простоя при изменении размера.
</b></details>

<details>
<summary>Какие облачные ресурсы часто масштабируют вертикально?</summary><br><b>

Например, экземпляры БД, кэша и обычные ВМ; особенно когда приложение не умеет распределять работу между узлами.
</b></details>

<details>
<summary>Что такое горизонтальное масштабирование?</summary><br><b>

Добавление узлов, между которыми распределяется нагрузка системы.
</b></details>

<details>
<summary>Что требуется для горизонтального масштабирования и каковы его сложности?</summary><br><b>

Нужен механизм распределения работы, например балансировщик или очередь, чтобы новые узлы действительно получали запросы.
Также требуется решить вопросы общего состояния, согласованности данных и координации.
</b></details>

<details>
<summary>Когда вы выберете вертикальное, а когда горизонтальное масштабирование?</summary><br><b>

Вертикальное — когда приложение плохо распределяется и хватает ресурсов большего узла; горизонтальное — когда работа разделима и нужна ёмкость/резервирование нескольких узлов. Учитывайте пределы, стоимость, состояние, перераспределение и простой. Эти способы можно сочетать.
</b></details>

<details>
<summary>Что такое устойчивость к сбоям и как её повысить?</summary><br><b>

Способность сохранять приемлемую работу и восстанавливаться при отказах. Меры: устранение single points, timeouts, ограниченные retries с jitter, bulkheads, circuit breakers, backpressure, резервные копии и проверенные процедуры. Резервирование без испытаний и наблюдаемости не доказывает устойчивость.
</b></details>

<details>
<summary>Что такое консистентное хеширование?</summary><br><b>

Ключи и узлы отображаются в пространство хешей так, что при изменении состава перемещается лишь часть ключей. Виртуальные узлы помогают распределению; требуется политика репликации и отказов. Консистентное хеширование не обеспечивает само по себе согласованность данных.
</b></details>

<details>
<summary>Как обновить сервисы на схеме без простоя foo.com?<br>
<img src="images/design/cdn-no-downtime.png" width="300x;" height="400px;"/>
</summary><br><b>

На схеме два origin-пути через балансировщики и CDN. Подготовьте новую версию и совместимую схему данных, проверьте readiness, переводите трафик постепенно, прекращайте новые запросы на старые экземпляры и дайте завершиться активным. Не обновляйте одновременно единственные экземпляры обоих origin. Версионируйте статические ресурсы CDN и предусмотрите откат; наличие CDN не скрывает отказ некэшируемого backend.
</b></details>

<details>
<summary>Какая проблема есть в следующей архитектуре и как её исправить?<br>

Производители или потребители могут перегрузиться и перестать отвечать.<br>
Добавьте очередь или потоковую платформу, например Kafka/Kinesis, и управление скоростью потребления. Потребители забирают работу по мере готовности. Ёмкость, хранение backlog и backpressure всё равно нужно проектировать: платформа не устраняет перегрузку автоматически.

<img src="images/design/producers_consumers_fix.png" width="300x;" height="200px;"/>
</b></details>

<details>
<summary>Небольшое увеличение входных данных резко увеличило время обработки. В чём может быть причина?<br>
<img src="images/design/input-process-output.png" width="300x;" height="200px;"/>
</summary><br><b>

Возможны квадратичный алгоритм, превышение памяти и переход к swap, изменение плана БД, исчерпание кэша или очереди. Измерьте профиль на нескольких размерах входа, время CPU/I/O, память и планы запросов. Корреляция с размером ещё не определяет причину.
</b></details>

<details>
<summary>Как масштабировать архитектуру предыдущего вопроса до сотен пользователей?</summary><br><b>

В предыдущем вопросе нет однозначной полной архитектуры, поэтому сначала нужны профиль запросов и SLO. Измерьте bottleneck, устраните его, затем добавляйте реплики, очередь/кэш или масштабирование БД по необходимости. Сотня пользователей без интенсивности запросов не задаёт требуемую ёмкость.
</b></details>

<a id="cache"></a>
#### Кэш

<details>
<summary>Что такое кэш и когда его использовать?</summary><br><b>

Копия/результат вычисления для ускорения повторного доступа. Полезен при повторяемом чтении и допустимой политике свежести. Определите ключ, TTL/инвалидацию, размер, поведение при промахе и cache stampede; не смешивайте данные разных пользователей в общем ключе.
</b></details>

<details>
<summary>Что такое распределённый кэш?</summary><br><b>

Кэш распределён по нескольким узлам для общей ёмкости и доступа приложений. Добавляет сетевые задержки, отказоустойчивость, распределение ключей и вопросы согласованности. Нужен fallback, чтобы отказ кэша не обрушил основную БД лавиной запросов.
</b></details>

<details>
<summary>Что такое политика вытеснения кэша?</summary><br><b>

Описание — [здесь](https://en.wikipedia.org/wiki/Cache_replacement_policies).
</b></details>

<details>
<summary>Какие политики вытеснения вы знаете?</summary><br><b>

Список — [здесь](https://en.wikipedia.org/wiki/Cache_replacement_policies).
</b></details>

<details>
<summary>Объясните политики вытеснения:

  * FIFO
  * LIFO
  * LRU</summary><br><b>

Подробнее — [здесь](https://en.wikipedia.org/wiki/Cache_replacement_policies).
</b></details>

<details>
<summary>Почему не хранить всё в кэше вместо БД?</summary><br><b>
Кэш и постоянное хранилище решают разные задачи.

Кэш ускоряет обращения, сохраняя часто используемые данные рядом с приложением, обычно в памяти или на быстром носителе. Записи могут вытесняться и теряться.

БД предназначена для долговременного управления данными, конкурентного доступа, ограничений целостности, индексов и запросов. Некоторые продукты совмещают роли, но гарантии хранения нужно оценивать явно.
</b></details>

<a id="hardware"></a>
## Оборудование

<details>
<summary>Что такое CPU?</summary><br><b>

Центральный процессор исполняет инструкции: арифметические, логические и управляющие операции, взаимодействие с памятью и устройствами. Это отличается от роли основной памяти и специализированных ускорителей, например GPU.
</b></details>

<details>
<summary>Что такое RAM?</summary><br><b>

Оперативная память хранит используемые сейчас код и данные ОС и приложений, предоставляя процессору быстрый доступ. Обычно она значительно быстрее HDD и SSD и теряет содержимое при отключении питания.
</b></details>

<details>
<summary>Что такое GPU?</summary><br><b>
Графический процессор — специализированный параллельный вычислитель, первоначально предназначенный для графики и видео, также используемый для общих вычислений и ML.

</b></details>

<details>
<summary>Что такое встроенная система?</summary><br><b>

Вычислительная система с процессором, памятью и вводом-выводом, выполняющая определённую функцию внутри более крупного электронного или механического устройства.
</b></details>

<details>
<summary>Приведите пример встроенной системы.</summary><br><b>

Микроконтроллер, управляющий цифровой панелью микроволновой печи.

Raspberry Pi также может стать частью встроенной системы при выполнении определённой функции устройства.

</b></details>

<details>
<summary>Какие типы хранения данных существуют?</summary><br><b>

Примеры хранения: HDD, SSD, оптические диски CD/DVD/Blu-ray, USB-накопители, карты памяти и сетевые хранилища NAS.
</b></details>

<details>
<summary>Что DevOps-команде учитывать при выборе оборудования?</summary><br>

Оборудование должно обеспечивать нужную скорость CI/CD, обратной связи и работу сервисов. Основные критерии:

1. **Характер нагрузки:**
   * CPU: важнее частота или количество ядер — зависит от задач.
   * RAM: достаточный объём для сборок, автоматизации и параллельной работы.
   * Хранение: ёмкость, задержка и скорость; SSD часто ускоряют операции.

2. **Возможность расширения:**
   * Горизонтальная: добавление узлов.
   * Вертикальная: увеличение RAM, CPU и других ресурсов узла.

3. **Сеть:**
   * Достаточная скорость получения кода и передачи данных.
   * Малая задержка для распределённых задач.
   * Резервные пути связи.

4. **Доступность:**
   * Резервирование дисков, питания и сети. RAID повышает устойчивость к отказу диска, но не заменяет резервные копии.

5. **Совместимость:**
   * Поддержка ОС, ПО, драйверов и целевых платформ.

6. **Энергоэффективность:**
   * Потребление энергии существенно влияет на стоимость крупных установок.

7. **Безопасность:**
   * Аппаратные механизмы, например TPM и проверенная загрузка.

8. **Удалённое управление и наблюдение:**
   * Контроллеры управления, например ILOM.
   * Доступность показателей состояния и производительности.

9. **Бюджет:**
   * Цена покупки и полная стоимость эксплуатации.

10. **Поддержка:**
   * Надёжность поставщика, гарантия и сроки ремонта.
   * Доступность драйверов, обновлений и опыта сообщества.

11. **Будущие потребности:**
   * Резерв под ожидаемый рост и новые задачи.

12. **Условия эксплуатации:**
   * Охлаждение и отвод тепла.
   * Габариты и место в стойке.
   * Основное и резервное электропитание.

13. **Гибридная инфраструктура:**
   * Совместимость и связность с облачными ресурсами.

14. **Жизненный цикл:**
   * Срок службы, окончания поддержки и план замены.

15. **Виртуализация:**
   * Поддержка гипервизоров, контейнерных нагрузок и нужных аппаратных функций.

16. **Ремонтопригодность:**
   * Возможность замены отдельных модулей и компонентов.

17. **Зависимость от поставщика:**
   * Оценка преимуществ и рисков единой платформы и альтернатив.

18. **Экологические аспекты:**
   * Энергоэффективность, ответственное производство и утилизация.

Выбор должен учитывать совместимость, производительность и бюджет, а также обслуживание, расширение и будущую замену.

</details>

<details>
<summary>Какую роль оборудование играет в аварийном восстановлении?</summary><br>

Оно обеспечивает ресурсы для продолжения работы и восстановления. Помимо процедур и ответственных людей, плану DR нужны:

1. **Резервное хранение данных:**
   * Ленточные системы, серверы резервного копирования и другие носители, включая копии на отдельной площадке.
   * Отказоустойчивые дисковые массивы; RAID не является резервной копией.

2. **Резервные вычислительные ресурсы:**
   * Серверы для замены вышедших из строя.
   * Балансировщики и средства переключения трафика на исправные узлы.

3. **Резервные площадки:**
   * Горячая: подготовлена к быстрому приёму нагрузки.
   * Холодная: требует развёртывания и восстановления данных, поэтому запускается дольше.
   * Тёплая: подготовлена частично, время восстановления промежуточное.

4. **Резервное питание:**
   * ИБП для коротких перерывов и корректного завершения работы.
   * Генераторы для длительных отключений.

5. **Сетевая инфраструктура:**
   * Независимые каналы и провайдеры.
   * Защищённый удалённый доступ для команды восстановления.

6. **Физическая инфраструктура:**
   * Стойки и организованное размещение оборудования.
   * Резервное охлаждение при отказе основной системы.

7. **Альтернативная связь:**
   * Спутниковая связь при недоступности обычной.
   * Радиосвязь или другие независимые каналы координации.

8. **Защита:**
   * Межсетевые экраны и обнаружение вторжений для резервной среды.
   * Физический контроль доступа и наблюдение.

9. **Совместимость оборудования:**
   * Стандартизированные конфигурации упрощают замену и восстановление.

10. **Средства проверки плана:**
   * Изолированные ресурсы для учений, чтобы тестировать восстановление и ёмкость без ущерба основной системе.

Оборудование нужно резервировать, обслуживать и регулярно проверять вместе со всем планом DR.

</details>

<details>
<summary>Что такое RAID?</summary><br>
<b>
Redundant Array of Independent Disks — объединение дисков в массив для увеличения производительности, ёмкости и/или устойчивости к отказам. Свойства зависят от уровня: например, RAID 0 не даёт избыточности, RAID 1 зеркалирует данные, RAID 5 использует чётность.

</b></details>

<details>
<summary>Что такое микроконтроллер?</summary><br>
<b>
Микросхема, объединяющая процессор, память и периферийные интерфейсы для управления встроенной системой.

</b></details>

<details>
<summary>Что такое NIC?</summary><br><b>
Network Interface Controller — сетевой контроллер, обеспечивающий подключение компьютера и обмен данными с сетью.

</b></details>

<details>
<summary>Что такое DMA?</summary><br><b>

Direct Memory Access — передача данных между устройством и основной памятью без копирования каждого элемента процессором. CPU настраивает операцию и может выполнять другую работу.
</b></details>

<details>
<summary>Что такое ОС реального времени?</summary><br><b>

RTOS предназначена для задач с заданными временными ограничениями. Важна предсказуемая верхняя граница задержек, а не просто высокая средняя скорость. Планирование часто использует приоритеты и вытеснение. Не всякая RTOS устроена одинаково, и обычные ОС также могут применять приоритеты и обработку событий.
</b></details>

<details>
<summary>Какие типы прерываний существуют?</summary><br><b>

В исходнике приведена архитектурно-зависимая классификация из шести групп:
* Внешние.
* Контрольные аппаратные ошибки (machine check).
* Ввод-вывод.
* Программные исключения.
* Перезапуск.
* Вызов супервизора (SVC).
</b></details>

## Большие данные

<details>
<summary>Что такое Big Data?</summary><br><b>

Обычно описывают через характеристики V; исходная модель Дага Лэйни включала первые три, позднее появились расширения:

* Volume — большой объём.
* Velocity — скорость поступления и обработки, включая потоки.
* Variety — разнообразие структурированных, полуструктурированных и неструктурированных данных.
* Veracity/Variability — достоверность и изменчивость данных.
</b></details>

<details>
<summary>Что такое DataOps и как он связан с DevOps?</summary><br><b>

DataOps сокращает цикл создания ценности из данных: от идеи до работающего аналитического продукта, отчёта или модели.
Он применяет практики Agile, DevOps и контроля качества процессов к аналитике и конвейерам данных.
</b></details>

<details>
<summary>Что такое архитектура данных?</summary><br><b>

По определению [talend.com](https://www.talend.com/resources/what-is-data-architecture):

Правила и организация сбора, хранения, преобразования, передачи и использования данных. Цель — предоставлять нужные и понятные данные тем, кому они нужны, в подходящее время.
</b></details>

<details>
<summary>Какие формы организации данных существуют?</summary><br><b>

* Структурированные: фиксированная схема полей и типов, например таблица.
* Полуструктурированные: содержат собственные структурные метки, например XML или JSON, без обязательной единой табличной схемы.
* Неструктурированные с точки зрения аналитической схемы: свободный текст, изображения и т. д.; у самих файлов при этом есть формат.
</b></details>

<details>
<summary>Что такое Data Warehouse?</summary><br><b>

[Описание в Wikipedia](https://en.wikipedia.org/wiki/Data_warehouse).
[Описание AWS](https://aws.amazon.com/data-warehouse).
</b></details>

<details>
<summary>Что такое Data Lake?</summary><br><b>

[Озеро данных — Wikipedia](https://en.wikipedia.org/wiki/Data_lake).
</b></details>

<details>
<summary>Чем озеро данных отличается от аналитического хранилища?</summary><br><b>

Data lake обычно хранит исходные данные разных форматов с последующим определением схемы чтения; warehouse организован под согласованную аналитическую модель и запросы. Lakehouse сближает подходы. В обоих случаях нужны каталог, качество, права и жизненный цикл — «озеро» не означает бесконтрольную свалку.
</b></details>

<details>
<summary>Что такое версионирование данных? Какие модели существуют?</summary><br><b>

Фиксация состояния данных, позволяющая воспроизвести анализ или модель. Подходы: неизменяемые снимки/партиции, версии объектов, журнал событий, версионируемые таблицы с time travel. Нужно фиксировать также схему, преобразования и входные зависимости; Git не подходит напрямую для любого объёма бинарных данных.
</b></details>

<details>
<summary>Что такое ETL?</summary><br><b>

Extract → Transform → Load: получить данные, преобразовать и загрузить в целевую систему. В ELT преобразование выполняют уже после загрузки. Нужны проверка качества, идемпотентность, контроль схемы, обработка ошибок и наблюдаемость конвейера.
</b></details>

#### Apache Hadoop

<details>
<summary>Что такое Hadoop?</summary><br><b>

</b></details>

<details>
<summary>Что такое Hadoop YARN?</summary><br><b>

Подсистема управления ресурсами кластера и планирования выполнения приложений.

<details>
<summary>Что такое Hadoop MapReduce?</summary><br><b>

Модель и механизм распределённой пакетной обработки больших наборов данных.
</b></details>

<details>
<summary>Что такое HDFS?</summary><br><b>

* Распределённая файловая система с высокой суммарной пропускной способностью.
* Пользователь видит единое пространство файлов, хотя данные распределены по узлам.
* Рассчитана на крупные файлы, в том числе терабайтного размера, и большие наборы данных.
* Имеет механизмы избыточности и восстановления после отказов.
* Особенно подходит для последовательной пакетной обработки, а не для произвольного доступа с малой задержкой.
</b></details>

<details>
<summary>Как устроена HDFS?</summary><br><b>

[Архитектура HDFS](http://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html).

* Управляющие узлы и узлы хранения.
* NameNode управляет метаданными, DataNode хранят блоки.
* Файл делится на блоки.
* Блоки размещаются на DataNode.
* NameNode хранит пространство имён и сведения о размещении; для его доступности нужна соответствующая HA-конфигурация.
</b></details>

<a id="ceph"></a>
## Ceph

<details>
<summary>Что такое Ceph?</summary><br><b>
Открытая распределённая система хранения, рассчитанная на масштабирование и отказоустойчивость. Часто применяется в облаках и ЦОД.
</b></details>

<details>
<summary>Верно ли, что Ceph отдаёт приоритет корректности и согласованности перед продолжением работы любой ценой?</summary><br><b>
Верно.
</b></details>

<details>
<summary>Какие интерфейсы хранения предоставляет Ceph?</summary><br><b>

* Объектный — RGW.
* Блочный — RBD.
* Файловый — CephFS.
</b></details>

<details>
<summary>Что такое RADOS?</summary><br><b>

* Reliable Autonomic Distributed Object Store — распределённая объектная основа Ceph.
* Предоставляет низкоуровневое хранение объектов.
* Обеспечивает строгую согласованность операций в своей модели.
* Служит основой блочного, файлового и объектного интерфейсов верхнего уровня.
</b></details>

<details>
<summary>Какие компоненты входят в RADOS?</summary><br><b>

* Monitor:
  * Поддерживает карты кластера и данные аутентификации.
  * Обеспечивает согласованный взгляд компонентов на критичное состояние.
  * Использует кворум и Paxos для согласования состояния.
* Manager:
  * Собирает оперативные показатели, например использование дисков и throughput.
  * Запускает расширяемые модули управления.
  * Один активный, для резервирования — один или несколько standby.
* OSD — Object Storage Daemon:
  * Хранит данные на HDD или SSD.
  * Обслуживает ввод-вывод клиентов и операции избыточности.
</b></details>

<details>
<summary>Как клиент читает данные Ceph?</summary><br><b>
Основные шаги:

1. Клиент инициирует чтение.
> **В роли клиента может выступать:**
>> * Клиент Ceph Block Device.
>> * Ceph Object Gateway.
>> * Другое приложение с клиентской библиотекой Ceph.


2. Получает актуальные карты кластера от Monitor, если их ещё нет.
3. Определяет PG по объекту и пулу; CRUSH и карты кластера позволяют определить обслуживающие OSD.
4. Обращается к нужному OSD и получает данные.


</b></details>

<details>
<summary>Как клиент записывает данные Ceph?</summary><br><b>
Основные шаги:

1. Клиент инициирует запись; в исходнике здесь ошибочно указано чтение.
2. Получает актуальные карты кластера от Monitor, если их ещё нет.
3. Определяет PG и набор обслуживающих OSD по картам кластера и правилам размещения.
4. Отправляет запись primary OSD. Тот координирует репликацию либо кодирование и распределение фрагментов для erasure-coded пула, после чего подтверждает операцию согласно гарантиям пула.

</b></details>

<details>
<summary>Что такое группы размещения (Placement Groups)?</summary><br><b>

В контексте Ceph PG — логические группы объектов для размещения и восстановления, а не AWS Placement Groups. Они уменьшают объём управления по сравнению с отдельным размещением каждого объекта. Число PG и autoscaler настраивают с учётом пулов и OSD. [Ceph PG](https://docs.ceph.com/en/latest/rados/operations/placement-groups/).
</b></details>

<details>
<summary>Объясните связь: объекты → пулы → placement groups → OSD.</summary><br><b>

Объект находится в логическом пуле с политикой репликации/кодирования. Хеш объекта/routing сопоставляется PG, а карта кластера и CRUSH определяют набор OSD для PG. Пул не является отдельным физическим диском; при изменении кластера группы могут перераспределяться.
</b></details>

<details>
<summary>Что такое OMAP?</summary><br><b>

Object Map — набор пар ключ–значение, прикреплённый к объекту RADOS и доступный через соответствующие операции. Используется верхними слоями для индексов/метаданных; это не отдельная SQL-БД и не то же самое, что произвольные пользовательские xattr файла.
</b></details>

<details>
<summary>Что такое Metadata Server и как он работает?</summary><br><b>

Ceph MDS обслуживает метаданные и операции пространства имён CephFS, например каталоги, имена и права. Содержимое файлов хранится в RADOS, а не проходит целиком через MDS. Для доступности нужны standby и подходящая конфигурация метаданных; MDS не требуется для одного лишь RBD/RGW.
</b></details>

<a id="packer"></a>
## Packer

<details>
<summary>Что такое Packer и для чего он нужен?</summary><br><b>

Packer автоматизирует создание образов машин.
Он позволяет установить ПО и выполнить основную настройку при сборке образа, чтобы ускорить последующее развёртывание экземпляров.
</b></details>

<details>
<summary>Packer следует модели «настройка → развёртывание» или «развёртывание → настройка»?</summary><br><b>

«Настройка → развёртывание». Преимущества:

1. Быстрее запуск: подготовка выполняется при сборке образа, а не повторяется целиком при каждом развёртывании.
2. Более воспроизводимая инфраструктура: экземпляры получают одинаковую основу, ошибки зависимостей можно выявить до развёртывания. Настройки времени запуска всё равно могут потребоваться.
</b></details>

<details>
<summary>Что такое семантическое версионирование?</summary><br><b>

Описание — [здесь](https://semver.org/):

```
Given a version number MAJOR.MINOR.PATCH, increment the:

MAJOR version when you make incompatible API changes
MINOR version when you add functionality in a backwards compatible manner
PATCH version when you make backwards compatible bug fixes
Additional labels for pre-release and build metadata are available as extensions to the MAJOR.MINOR.PATCH format.
```
</b></details>
