## Вопросы

<a id="global-infrastructure"></a>
### Глобальная инфраструктура

<details>
<summary>Объясните понятия:

* Зона.
* Регион.
</summary><br><b>

Регионы GCP — географические области размещения центров обработки данных по всему миру.<br>

Каждый регион содержит несколько изолированных зон. Зона включает инфраструктуру ЦОД с резервированием сети, подключений и электропитания. Использование нескольких зон повышает доступность при отказе одной из них.
</b></details>

<details>
<summary>Верно ли, что регионы GCP проектируются изолированными друг от друга?</summary><br><b>

Да, в контексте изоляции отказов региональной инфраструктуры.
</b></details>

<details>
<summary>Что учитывать при выборе региона GCP для нового приложения?</summary><br><b>

* Доступность сервисов: не все продукты и возможности есть в каждом регионе.
* Задержку: размещение ближе к пользователям обычно снижает сетевую задержку.
* Требования к размещению данных: иногда данные должны оставаться в определённой стране или регионе.
* Стоимость: цены одной услуги могут различаться по регионам.
</b></details>

<details>
<summary>Верно ли, что все сервисы GCP доступны во всех регионах и зонах?</summary><br><b>

Нет. Доступность продуктов по регионам указана [здесь](https://cloud.google.com/about/locations).
</b></details>

<a id="resource-hierarchy"></a>
### Иерархия ресурсов

<details>
<summary>Объясните иерархию ресурсов GCP.</summary>

Организация → необязательные папки → проекты → ресурсы сервисов. У проекта один родитель в иерархии; для личного аккаунта проект может существовать без организации. Иерархия задаёт области политик и управления, а не обязательное соответствие «один проект — одно приложение». Не путайте project ID, display name и числовой project number.
</details>

<details>
<summary>Верно ли, что проект может содержать одну или несколько организаций?</summary><br><b>

Нет, наоборот: организация может содержать папки и проекты.
</b></details>

<details>
<summary>Верно ли, что ресурс должен быть связан хотя бы с одним проектом?</summary><br><b>

Для обычных сервисных ресурсов, рассматриваемых в этом разделе, — да: они создаются в проекте. Саму организацию и папки не следует путать с ресурсами этого уровня.
</b></details>

<details>
<summary>Верно ли, что название проекта должно быть глобально уникальным?</summary><br><b>

Примечание к переводу: исходник отвечает «да», но нужно различать отображаемое название и идентификатор. Глобальная уникальность требуется для Project ID, а не для отображаемого имени проекта.
</b></details>

<a id="iam-and-roles"></a>
### IAM и роли

<details>
<summary>Объясните роли и разрешения.</summary>

Разрешение описывает допустимое действие над ресурсом; роль объединяет разрешения. Различайте базовые, предопределённые и пользовательские роли. Owner — широкая базовая роль, но не универсальный обход всех ограничений. Вместо запоминания устаревающего числа permissions выбирайте минимально необходимые роли для конкретных операций.
</details>

<details>
<summary>Верно ли, что разрешающая политика родителя всегда имеет приоритет над ограничивающей политикой потомка?</summary>

Нет. Наследуемые allow-разрешения складываются: простое отсутствие локального allow не отзывает доступ, выданный выше. Но применимые deny-правила и Principal Access Boundary могут ограничить его. Учитываются условия и область действия, а не правило «родитель всегда сильнее». [IAM policy evaluation](https://docs.cloud.google.com/iam/docs/policy-types).
</details>

<a id="labels-and-tags"></a>
### Метки и теги

<details>
<summary>Что такое labels?</summary><br><b>

Метки можно представить как наклейки на ресурсах. Они упрощают поиск и группировку: например, метка web-app помогает найти ресурсы соответствующего приложения.
</b></details>

<details>
<summary>Приведите примеры использования меток GCP.</summary><br><b>

* Место размещения или центр затрат.
* Проект, среда или папка.
* Тип сервиса.
* Владелец сервиса.
* Тип приложения.
* Владелец приложения.
</b></details>

<details>
<summary>Что такое сетевые теги и чем они отличаются от меток?</summary>

Network tags — строки, назначаемые VM для выбора целей/источников в поддерживающих их сетевых правилах. Labels — аннотации ресурсов для организации и учёта. Отдельно существуют Resource Manager tags: управляемые key/value/binding ресурсы с IAM, наследованием и применением в условиях политик. Эти три механизма не взаимозаменяемы. [Tags и labels](https://docs.cloud.google.com/resource-manager/docs/tags/tags-overview).
</details>

<a id="other"></a>
### Разное

<details>
<summary>Что вы знаете о сетях GCP?</summary><br><b>

VPC — виртуальный аналог физической сети, реализованный внутри сети Google. В GCP сеть VPC является глобальным ресурсом, а подсети — региональными.

Есть два режима создания VPC:

1. Автоматический: в каждом регионе автоматически создаётся подсеть.
2. Пользовательский: подсети автоматически не создаются; пользователь полностью управляет их созданием.
</b></details>

<details>
<summary>Объясните назначение Cloud Functions.</summary>

Историческое название serverless-функций Google Cloud. Cloud Functions 2nd gen теперь называется Cloud Run functions; Cloud Functions API и соответствующие команды продолжают поддерживаться. Функции запускаются по HTTP или событиям, а ограничения зависят от поколения, runtime и способа развёртывания. Не смешивайте 1st gen и современные Cloud Run services. [Сравнение вариантов](https://docs.cloud.google.com/run/docs/functions/comparison).
</details>

<details>
<summary>Что такое Cloud Datastore?</summary>

Историческая NoSQL-база Google Cloud. Сейчас соответствующая совместимость предоставляется Firestore in Datastore mode, отдельный Datastore как новый продукт не предлагается. Поддерживаются entities, индексы, транзакции и Datastore API/GQL; это не реляционный SQL с произвольными JOIN. Не переносите старые ограничения консистентности оригинального Datastore на современный режим без проверки. [Обзор](https://docs.cloud.google.com/datastore/docs/concepts/overview).
</details>

<details>
<summary>Для чего нужны сетевые теги?</summary><br><b>

Они позволяют применять правила брандмауэра и маршруты к конкретным экземплярам или группам экземпляров. В правилах используются теги назначения и источника.
</b></details>

<details>
<summary>Что такое журналы сетевых потоков и где их включить?</summary>

VPC Flow Logs — агрегированные и выборочные записи сетевых потоков, а не полный packet capture. Учитывайте sampling, фильтры, доступ и хранение логов. Для существующей подсети через Compute Engine API:

```bash
gcloud compute networks subnets update SUBNET_NAME \
  --region=REGION --project=PROJECT_ID --enable-flow-logs
```

Есть также конфигурации через Network Management API; возможности и охват отличаются. [Настройка Flow Logs](https://docs.cloud.google.com/vpc/docs/using-flow-logs).
</details>

<details>
<summary>Как вывести список бакетов?</summary>

Для выбранного проекта используйте стабильную команду:

```bash
gcloud storage buckets list --project=PROJECT_ID
```

`PROJECT_ID` замените своим ID. Старый `gcloud alpha storage ls` для нового примера не нужен. Список виден в пределах доступных прав. [Справка CLI](https://docs.cloud.google.com/sdk/gcloud/reference/storage/buckets/list).
</details>

<details>
<summary>Какой ключ метаданных Compute позволяет запускать код при старте?</summary><br><b>

`startup-script`. В оригинале опечатка: startap-script.
</b></details>

<details>
<summary>Что делает команда gcloud deployment-manager deployments create?</summary>

Исторически создавала deployment из конфигурации Deployment Manager. Это не рекомендация для нового проекта: стандартная поддержка прекращена с 1 апреля 2026 года, новые пользователи с 30 июня 2026 года не могут включить API или создать первый deployment. Для существующих пользователей объявлен переходный период до 30 июня 2027 года с ограничениями поддержки. Проверьте действующий план миграции на Infra Manager или другой подходящий IaC-инструмент. [Официальное объявление](https://docs.cloud.google.com/deployment-manager/docs/deprecations).
</details>

<details>
<summary>Что такое Cloud Code?</summary><br><b>

Набор инструментов для написания, запуска и отладки приложений Kubernetes в GCP. Предоставляет средства быстрой итеративной разработки, отладки и запуска в средах Kubernetes.
</b></details>

Управляемый сервис Kubernetes в GCP для развёртывания, управления и масштабирования контейнерных приложений на инфраструктуре Google.

<a id="anthos"></a>
### Anthos

Названия ниже сохранены для понимания старых систем. Сверено 5 ноября 2026 года: прежние возможности Anthos/GKE Enterprise сейчас относятся к GKE и отдельным связанным продуктам; GKE описывается как единое предложение без прежних editions/tiers. Не используйте старый список брендов как текущую матрицу доступности. [Изменения GKE](https://docs.cloud.google.com/kubernetes-engine/enterprise/docs/release-notes).

<details>
<summary>Что такое Anthos?</summary>

Исторический бренд Google для управления контейнерными приложениями в облаке и локальной среде. Полезные идеи — fleet/multicluster management, декларативные политики, конфигурация и service mesh. Текущие названия, поддержку конкретной платформы и биллинг проверяют по документации GKE и связанных продуктов; слово Anthos не гарантирует прежний набор возможностей.
</details>

<details>
<summary>Перечислите технические компоненты Anthos.</summary>

В старых материалах встречаются GKE, Anthos Config Management, Anthos Service Mesh и Cloud Run for Anthos. При чтении современных документов сопоставляйте задачи с GKE/fleets, Config Sync/Policy Controller, Cloud Service Mesh и Knative serving. Это карта понятий, а не утверждение, что все компоненты включены в одну лицензию или работают на любой платформе.
</details>

<details>
<summary>Какая вычислительная среда является основной для управления рабочими нагрузками Anthos?</summary><br><b>

Google Kubernetes Engine (GKE).
</b></details>

<details>
<summary>Как в Anthos организованы плоскость управления и узлы GKE?</summary><br><b>

В описанной архитектуре GCP клиентам предоставляется доступ к API-серверу Kubernetes, а остальные компоненты плоскости управления обслуживаются платформой. Экземпляры рабочих узлов проекта управляются средствами Compute Engine.
</b></details>

<details>
<summary>Какие варианты балансировки нагрузки доступны?</summary><br><b>

* Сетевая балансировка L4 и HTTP(S)-балансировка L7 — управляемые сервисы, не требующие самостоятельного обслуживания балансировщиков.
* Ingress for Anthos — балансировка трафика приложения между несколькими кластерами GKE.
</b></details>

<details>
<summary>Можно ли развернуть Anthos в AWS?</summary>

Старое название Anthos on AWS относилось к GKE on AWS. Этот продукт находится в maintenance mode с 17 марта 2025 года; прекращение поддержки и отключение API объявлены на 17 марта 2027 года. Аналогичная дата объявлена для GKE on Azure. План миграции нужно строить с учётом конкретных используемых интеграций. [AWS](https://docs.cloud.google.com/kubernetes-engine/multi-cloud/docs/aws/deprecations/deprecation-announcement), [Azure](https://docs.cloud.google.com/kubernetes-engine/multi-cloud/docs/azure/deprecations/deprecation-announcement).
</details>

<details>
<summary>Перечислите корпоративные возможности безопасности Anthos.</summary><br><b>

* **Плоскость управления.** GCP обслуживает компоненты управления Kubernetes. Доступ к API-серверу ограничивают разрешёнными сетями и настройками частного кластера, включая использование частного адреса.
* **Узлы.** В исходнике описаны экземпляры Compute Engine с Container-Optimized OS: ограниченные сетевые правила и учётные записи, защита системных файлов. GKE Sandbox усиливает изоляцию рабочих нагрузок, в том числе при совместном использовании среды разными арендаторами.
* **Сеть.** Программно-определяемая сеть обеспечивает связь подов. Сетевые политики ограничивают входящие и исходящие подключения, а для внешнего трафика можно задавать разрешённые диапазоны CIDR.
* **Рабочие нагрузки.** Ограниченные привилегии и профили безопасности уменьшают доступ контейнеров к системе. Workload Identity связывает удостоверения рабочих нагрузок Kubernetes с разрешениями Google Cloud. Приведённые в оригинале стандартные настройки AppArmor и среды контейнеров зависят от конкретной конфигурации.
* **Аудит.** Администраторы могут сохранять, запрашивать и обрабатывать события среды, а также настраивать оповещения.
</b></details>

<details>
<summary>Как приложения локальных кластеров Anthos GKE могут безопасно подключаться к Google Cloud?</summary>

Разделяйте сетевой путь, шифрование и удостоверения. VPN/Interconnect с нужной маршрутизацией обеспечивает связность; TLS и корректная аутентификация защищают приложение. Для доступа к API нужны IAM и подходящая федерация идентичностей либо другой поддерживаемый механизм. Cloud KMS управляет ключами, но не создаёт сеть и не заменяет авторизацию API.
</details>

<details>
<summary>Что такое сетевой режим Island Mode в локальном Anthos GKE?</summary><br><b>

Поды напрямую общаются внутри кластера, но их адреса недоступны непосредственно извне. Кластер образует сетевой «остров».
</b></details>

<details>
<summary>Объясните Anthos Config Management.</summary>

Исторический набор управления конфигурациями и политиками. Современный Config Sync согласует ресурсы кластеров с желаемым состоянием из Git, OCI или Helm. Policy Controller — связанная, но отдельная функция проверки политик; синхронизация и admission enforcement — разные задачи. [Config Sync](https://docs.cloud.google.com/kubernetes-engine/config-sync/docs/overview).
</details>

<details>
<summary>Чем полезен Anthos Config Management?</summary>

Версионируемые изменения, review и reconciliation уменьшают ручной drift. Но ошибочная декларация тоже распространяется автоматически: нужны проверки, разграничение прав, контролируемое продвижение и наблюдение за состоянием синхронизации. Откат конфигурации не восстанавливает автоматически потерянные данные.
</details>

<details>
<summary>Что такое Anthos Service Mesh?</summary>

Историческое название связанного предложения service mesh. Современная документация Cloud Service Mesh охватывает бывших клиентов Anthos Service Mesh и Traffic Director. Возможности и API различаются для GKE, VM и внешних платформ. [Обзор](https://docs.cloud.google.com/service-mesh/docs/overview).
</details>

<details>
<summary>Назовите две основные части Anthos Service Mesh.</summary>

Data plane обрабатывает трафик через прокси либо поддерживаемые proxyless-клиенты. Control plane распространяет конфигурацию и политики. Управляемость и место размещения control plane зависят от варианта продукта и платформы; не всякий внешний кластер получает ту же управляемую схему, что GKE в Google Cloud.
</details>

<details>
<summary>Какие компоненты управляемой плоскости управления Anthos Service Mesh перечислены в исходной архитектуре?</summary>

В исходной схеме перечислялись Traffic Director, управляемый CA и эксплуатационные сервисы. Это исторический рисунок, а не неизменный состав продукта. Для действующей установки определите API, реализацию control plane, CA и поддерживаемый способ обновления по документации своей версии Cloud Service Mesh.
</details>

<details>
<summary>Чем полезен Anthos Service Mesh?</summary><br><b>

Объединение инструментов даёт следующие эксплуатационные преимущества:

* **Единая наблюдаемость.** Прокси передают сведения о межсервисном обмене, из которых строится граф зависимостей. Заголовки помогают распределённой трассировке; собираются журналы и метрики задержек, ошибок и доступности.
* **Гибкое управление трафиком.** Предоставляются точные настройки как входящего и исходящего трафика, так и обмена внутри mesh.
* **Безопасность на основе политик.** Единые правила применяются к взаимодействию сервисов независимо от различий протоколов и сред выполнения.
</b></details>

<details>
<summary>Назовите сценарии управления трафиком в Anthos Service Mesh.</summary><br><b>

* Разделение трафика между версиями для канареечного развёртывания или A/B-тестирования.
* Circuit breaking для предотвращения каскадных отказов.
* Внедрение сбоев для проверки устойчивости.
* Маршрутизация между сервисами и версиями на основе HTTP-заголовков.
</b></details>

<details>
<summary>Что такое Cloud Run for Anthos?</summary>

Историческое название Knative serving на Kubernetes. Это отдельный вариант от полностью управляемого Cloud Run: кластер и его зависимости нужно подготовить и обслуживать. Не путайте масштабирование workload до нуля с отсутствием стоимости самого кластера. [Текущая документация](https://docs.cloud.google.com/kubernetes-engine/enterprise/knative-serving/docs/console).
</details>

<details>
<summary>Как Cloud Run for Anthos упрощает эксплуатацию?</summary><br><b>

Платформенные команды могут использовать его, чтобы упростить разработчикам тестирование, развёртывание и запуск приложений.

* **Переход с обычных развёртываний Kubernetes.** Вместо отдельной настройки Deployment, Service, HPA и балансировки используется описание сервиса Knative. Оно объединяет настройки запуска, масштабирования и обслуживания трафика, упрощая изменение конфигураций и откат.
* **Автомасштабирование.** При резком росте трафика увеличивается количество экземпляров, чтобы снизить перегрузку.
* **Сеть.** Встроенная балансировка и разделение трафика между версиями приложения.
* **Выпуски и развёртывания.** Ревизии API Knative описывают версии и конфигурации; разделение трафика позволяет выполнять канареечные выпуски.
* **Мониторинг.** Сбор задержек, доли ошибок и количества запросов в секунду.
</b></details>

<details>
<summary>Назовите три высокоуровневые возможности автомасштабирования Cloud Run for Anthos, которые в исходнике противопоставлены базовым средствам Kubernetes.</summary><br><b>

* **Быстрое масштабирование по запросам.** Автомасштабирование использует метрики запросов для реакции на всплески трафика.
* **Управление конкурентностью.** Ограничивается число одновременно обрабатываемых запросов на контейнер. Дополнительные контейнеры и буферизация помогают обслуживать всплески без перегрузки.
* **Масштабирование до нуля.** При отсутствии активности приложение можно уменьшить до нуля экземпляров. Эту возможность можно отключить, чтобы избежать холодных запусков.
</b></details>

<details>
<summary>Назовите сценарии применения Cloud Run for Anthos.</summary><br><b>

В исходнике он рассматривается как платформа для приложений без состояния и без привязки сессии к экземпляру. Примеры:

* Предсказания моделей машинного обучения, например контейнеры TensorFlow Serving.
* API-шлюзы, промежуточные API-сервисы, веб-интерфейсы и микросервисы.
* Обработчики событий и ETL.
</b></details>
