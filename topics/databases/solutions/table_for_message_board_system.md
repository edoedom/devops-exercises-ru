## Схема базы данных для доски сообщений

<a id="instructions"></a>
### Требования

Хранить пользователей, сообщения и ответы, категории, упоминания, а также кто и когда просмотрел сообщение. Это одна из возможных моделей. В исходном решении не было таблиц просмотров и категорий; ниже требования покрыты явно.

<a id="solution"></a>
### Решение

| Таблица | Основные поля и ключи | Назначение |
|---|---|---|
| users | id PK, display_name TEXT, contact_email TEXT NULL | Минимальные данные пользователя |
| boards | id PK, name TEXT | Доски/пространства сообщений |
| board_members | PK(board_id, user_id), active | Участие пользователя в доске |
| messages | id PK, board_id, author_id, reply_to_id NULL, body, created_at | Текст и ссылка на родительское сообщение |
| categories | id PK, board_id, name; UNIQUE(board_id, name) | Категории конкретной доски |
| message_categories | PK(message_id, category_id), board_id | Связь сообщения с несколькими категориями |
| message_mentions | PK(message_id, user_id), board_id | Упомянутые участники доски |
| message_views | PK(message_id, user_id, viewed_at), board_id | История просмотров, включая повторные |

[Исполняемый пример SQLite](../examples/message_board/schema.sql) дополняет проектирование, хотя писать SQL в исходном задании не обязательно. Для PostgreSQL используйте подходящие identity/BIGINT и TIMESTAMPTZ; не копируйте SQLite-specific STRICT/PRAGMA/trigger syntax напрямую.

### Ограничения целостности

- Автор, упомянутый пользователь и зритель должны иметь запись участия в соответствующей доске. Составные FK не позволяют связать сообщения, категории или родителей из разных досок.
- Отдельное membership active не заменяет авторизацию: приложение проверяет активность, права чтения/записи и доступ к персональным данным. База не определяет, кто именно выполняет SQL-запрос.
- Родитель и доска сообщения после вставки неизменяемы. Немедленные FK и запрет ссылки на себя сохраняют ацикличность при обычной работе приложения. Не откладывайте проверки и не отключайте их, если рассчитываете на это свойство.
- Удаление связанных объектов ограничено RESTRICT: нельзя молча потерять историю просмотров или ответов. Для продукта отдельно спроектируйте архивирование, удаление/анонимизацию и срок хранения. Необязательные DOB, пол и телефон не стоит собирать без цели.
- Повторный просмотр в другое время сохраняется. Два события одного пользователя в тот же момент считаются одним: если нужна точная идентичность событий при одинаковом времени, добавьте event_id.

В SQLite FK включаются для каждого соединения **до** начала транзакции: `PRAGMA foreign_keys = ON`. Пример требует SQLite 3.37+; версия доступна через `sqlite3.sqlite_version` в Python. Времена здесь — TEXT с канонической UTC-записью, которую обеспечивает приложение; это не полноценный тип timestamp. Для временной сортировки все строки должны иметь один формат и часовую зону.

### Проверка

Из корня после установки requirements-dev.txt выполните `bash scripts/run_ci.sh`. Регрессионные тесты проверяют допустимые ответы/упоминания, повторные просмотры, запрет ссылок между досками, неверного автора, изменения родителя и удаления родителя с ответами. Тесты создают только SQLite in-memory и не обращаются к сети.

Источники: [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html), [PostgreSQL date/time](https://www.postgresql.org/docs/current/datatype-datetime.html).
