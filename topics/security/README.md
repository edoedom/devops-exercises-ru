[Википедия](https://en.wikipedia.org/wiki/Certificate_authority): удостоверяющий центр (CA) выпускает и подписывает цифровые сертификаты.

Сертификат связывает открытый ключ с удостоверяемым субъектом, например сайтом. * Срок действия.
* Имя субъекта.
* Сведения об открытом ключе субъекта.

При обычной проверке доверия к сайту строится цепочка от его сертификата через промежуточные центры к доверенному корневому сертификату. RBAC связывает доступ с рабочими функциями: со временем человек может менять роли и обязанности по отношению к ИТ-системам.

<details>
<summary>Что такое единый вход — SSO?</summary><br><b>

SSO позволяет пользователю один раз войти в систему, после чего получать доступ к ресурсам нескольких приложений без повторного ввода учётных данных для каждого из них.
</b></details>

<details>
<summary>Как Kerberos обеспечивает единый вход?</summary><br><b>

Пользователь один раз подтверждает свою личность и получает у доверенного сервера аутентификации билет TGT — Ticket Granting Ticket. В течение срока действия его можно использовать для получения сервисных билетов к различным ресурсам.

Благодаря билетам пользователю не нужно заново вводить пароль для каждого сервиса, интегрированного с Kerberos. Сам TGT предъявляется службе выдачи билетов, а целевому сервису — соответствующий сервисный билет.
</b></details>

<details>
<summary>Kerberos использует симметричное или асимметричное шифрование?</summary><br><b>

В базовой схеме Kerberos используется симметричная криптография с общими секретами. В исходнике написано «исключительно симметричная»; это не учитывает расширения начальной аутентификации с открытым ключом, например PKINIT.

Спецификация расширения: https://www.rfc-editor.org/rfc/rfc4556.html
</b></details>

<details>
<summary>Объясните многофакторную аутентификацию — MFA.</summary><br><b>

MFA требует подтверждений из нескольких различных категорий факторов. Двухфакторная аутентификация, 2FA, — частный случай MFA.

Категории: знание, например пароль или PIN; владение, например смарт-карта; биометрический признак, например отпечаток пальца. Два пароля сами по себе не являются двумя разными факторами.

#### Безопасность — пароли

<details>
<summary>Как вы управляете секретными данными, например паролями, в разных инструментах и платформах?</summary><br><b>
</b></details>

<details>
<summary>Какие атаки на пароли вы знаете?</summary><br><b>

* Словарная атака.
* Полный перебор.
* Password spraying — проверка небольшого набора распространённых паролей для множества учётных записей.
* Социальная инженерия: фишинг, голосовой фишинг (vishing), целевые атаки на руководителей и других значимых сотрудников (whaling).

В исходном перечне whaling повторялся дважды.
</b></details>

<details>
<summary>Как снизить риск атак на пароли?</summary><br><b>

* Применять надёжную парольную политику.
* Не использовать один пароль повторно.
* Использовать CAPTCHA там, где это уместно.
* Обучать сотрудников распознавать социальную инженерию.
* Применять аутентификацию с учётом риска.
* Ограничивать частоту попыток.
* Использовать MFA.
</b></details>

<details>
<summary>Что такое соль пароля? От какой атаки она помогает?</summary><br><b>

Соль — дополнительное значение, используемое вместе с паролем при вычислении его хеша. Для разных записей паролей должна использоваться разная соль, а при проверке — сохранённая соль именно этой записи.

Поэтому одинаковые пароли разных пользователей дают разные хеши. Соль противодействует применению заранее вычисленных таблиц, включая радужные: вычисления пришлось бы повторять для каждой соли отдельно.
</b></details>

<a id="security---cookies"></a>
#### Безопасность — cookie

<details>
<summary>Что такое cookie? Объясните аутентификацию с их использованием.</summary><br><b>
</b></details>

<details>
<summary>Верно ли, что аутентификация через cookie требует хранения состояния?</summary><br><b>

Для описанной ниже схемы серверных сессий — да: браузер хранит cookie с идентификатором, а сервер — состояние сессии.

Само использование cookie не требует серверного хранилища сессий: cookie может содержать и подписанный токен. Исходное утверждение относится к конкретной схеме, а не ко всем cookie.
</b></details>

<details>
<summary>Опишите процесс работы с сессионными cookie.</summary><br><b>

1. Пользователь вводит учётные данные.
2. Сервер проверяет их, создаёт сессию и сохраняет её в хранилище.
3. В браузер устанавливается cookie с идентификатором сессии.
4. При следующих запросах сервер проверяет идентификатор по хранилищу.
5. При выходе сессия прекращается на сервере, а cookie удаляется у клиента.
</b></details>

<a id="security---ssh"></a>
#### Безопасность — SSH

<details>
<summary>Что такое SSH и как он работает?</summary><br><b>

[Определение Википедии](https://en.wikipedia.org/wiki/SSH_(Secure_Shell)): SSH, или Secure Shell, — криптографический сетевой протокол для безопасного использования сетевых сервисов через незащищённую сеть.

[Определение Hostinger](https://www.hostinger.com/tutorials/ssh-tutorial-how-does-ssh-work): протокол удалённого администрирования, позволяющий управлять серверами через интернет.

Объяснение работы приведено [в этой статье](https://www.hostinger.com/tutorials/ssh-tutorial-how-does-ssh-work).
</b></details>

<details>
<summary>Какую роль играет ключ SSH?</summary><br><b>

[Википедия](https://en.wikipedia.org/wiki/Secure_Shell): SSH использует криптографию с открытым ключом для аутентификации удалённой стороны и пользователя.

Закрытый ключ пользователя хранится у него, а разрешённый открытый ключ размещается на сервере. При аутентификации клиент доказывает владение закрытым ключом, не передавая его серверу. Ключ хоста отдельно помогает клиенту проверить сервер.

**Уточнение к переводу:** исходник ошибочно описывает пользовательскую пару ключей как средство шифрования всего обмена. Данные сеанса защищаются согласованными симметричными ключами.

Описание транспортного протокола: https://www.rfc-editor.org/rfc/rfc4253.html
</b></details>

<a id="security---cryptography"></a>
#### Безопасность — криптография

<details>
<summary>Объясните симметричное шифрование.</summary><br><b>

Для шифрования и расшифрования используется один и тот же секретный ключ.
</b></details>

<details>
<summary>Объясните асимметричное шифрование.</summary><br><b>

Используется связанная пара разных ключей — открытый и закрытый. В схемах шифрования открытым ключом зашифрованные данные расшифровываются соответствующим закрытым ключом.
</b></details>

<details>
<summary>Что такое обмен или согласование ключей в криптографии?</summary><br><b>

[Википедия](https://en.wikipedia.org/wiki/Key_exchange): способ, с помощью которого стороны получают криптографические ключи для использования криптографического алгоритма. В зависимости от схемы ключ передаётся защищённым способом либо совместно вырабатывается сторонами.
</b></details>

<details>
<summary>Верно ли, что симметричное шифрование использует открытый и закрытый ключи, причём закрытый расшифровывает данные, зашифрованные открытым?</summary><br><b>

Нет. Это описание асимметричного шифрования.
</b></details>

<details>
<summary>Можно ли вычислить закрытый ключ по открытому?</summary><br><b>

Для корректно выбранной и реализованной криптосистемы это должно быть вычислительно неосуществимо с доступными ресурсами. Краткое «нет» в исходнике не означает математической невозможности перебора или отсутствия атак на слабые алгоритмы.
</b></details>

<details>
<summary>Верно ли, что асимметричная криптография не шифрует весь сеанс SSH?</summary><br><b>

Да. Она участвует в согласовании ключей и аутентификации; основной поток данных защищается симметричными алгоритмами.
</b></details>

<details>
<summary>Что такое хеширование?</summary><br><b>

Преобразование данных произвольного размера в значение фиксированной длины — хеш, или дайджест. Один из вариантов применения — проверка того, что данные не изменились.
</b></details>

<details>
<summary>Чем хеширование отличается от шифрования?</summary><br><b>

Зашифрованные данные можно расшифровать с нужным ключом. Криптографическое хеширование — одностороннее преобразование: обратной операции восстановления исходных данных по хешу не предусмотрено.
</b></details>

<details>
<summary>Как хеш-функции используются в SSH?</summary><br><b>

В составе криптографических механизмов они участвуют в проверке подлинности и целостности сообщений. Обычный хеш без аутентификации сам по себе не защищает от преднамеренной подмены.
</b></details>

<details>
<summary>Что такое XSS?</summary><br><b>

Межсайтовый скриптинг (Cross-Site Scripting) — атака, при которой недоверенный код выполняется браузером в контексте сайта. Исходник описывает отражённый вариант: код не сохраняется в приложении, а атака затрагивает пользователей, открывших специально подготовленную ссылку или страницу. Существуют и другие разновидности XSS.

Успешная атака может дать доступ к данным страницы, доступным скрипту cookie и токенам либо позволить действия от имени пользователя. Доступ к конкретным данным зависит от защитных механизмов браузера и приложения.

При проверке изучают точки ввода и способы обработки данных: параметры HTTP, POST-данные, скрытые поля форм, значения переключателей и списков. Затем анализируют, могут ли эти значения попасть в опасный контекст вывода, и проверяют выявленные случаи в разрешённой тестовой среде.
</b></details>

<details>
<summary>Что такое SQL-инъекция и как от неё защищаться?</summary><br><b>

SQL-инъекция возникает, когда пользовательские данные интерпретируются как часть SQL-команды. В результате атакующий может, например, получить доступ к конфиденциальным данным приложения.

В оригинале упомянуты хранимые процедуры и очистка ввода. **Уточнение:** сама по себе хранимая процедура не гарантирует защиту, если небезопасно строит динамический SQL. Основной подход — параметризованные запросы, при которых данные отделены от структуры команды. Для элементов структуры, не поддерживающих параметры, используют фиксированный набор допустимых вариантов.

Источник уточнения: https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html

<summary>Что такое CSRF и как от него защищаться?</summary><br><b>

Межсайтовая подделка запроса (Cross-Site Request Forgery) заставляет браузер пользователя отправить нежелательный запрос приложению, в котором уже действует его сеанс. Отправитель вычисляет значение для определённой версии, а получатель повторяет вычисление и сравнивает результаты. Различие указывает на изменение данных при передаче или хранении.

**Уточнение к переводу:** совпадение с суммой, полученной по недоверенному каналу, само по себе не доказывает отсутствие злонамеренной подмены: атакующий может заменить и файл, и опубликованное значение. Нужны доверенный источник эталона и подходящий криптографический алгоритм. Контрольная сумма также не доказывает безопасность содержимого самого пакета.
</b></details>

<a id="microsegmentation"></a>
## Микросегментация

<details>
<summary>Что такое микросегментация?</summary><br><b>

Метод обеспечения безопасности, управляющий сетевым доступом между конечными точками: процессами, устройствами и экземплярами систем.

Политики ограничивают взаимодействие на основе подходов Zero Trust и наименьших привилегий. Ожидаемые результаты — сокращение возможностей атаки и ограничение распространения последствий компрометации.
</b></details>

<details>
<summary>Зачем нужна микросегментация? Почему недостаточно обычного межсетевого экрана?</summary><br><b>

Периметровая защита прежде всего контролирует трафик между внутренней средой и внешним миром — north–south. Внутренний обмен между системами — east–west — при этом может оставаться недостаточно ограниченным.

Микросегментация позволяет детально управлять именно такими связями. Это не означает, что межсетевые экраны принципиально не могут фильтровать внутренний трафик.
</b></details>

<details>
<summary>Как реализуют микросегментацию?</summary><br><b>

* **Средствами облака:** группы безопасности, облачные межсетевые экраны и другие встроенные возможности.
* **С помощью агентов:** программы на экземплярах систем, сервисах и других конечных точках применяют правила доступа.
* **На уровне сети:** настройки сетевого оборудования разделяют и ограничивают взаимодействие.
</b></details>

<details>
<summary>Что такое эфемерные среды в контексте микросегментации?</summary><br><b>

Это короткоживущие ресурсы, например контейнеры и бессерверные функции, которые быстро создаются и исчезают.

Правила безопасности должны успевать за такими изменениями. Микросегментация предоставляет каждому ресурсу только необходимый сетевой доступ.
</b></details>

<details>
<summary>Как микросегментация препятствует горизонтальному перемещению атакующего?</summary><br><b>

Она задаёт точные правила взаимодействия систем и сервисов. Компрометация одной системы не должна автоматически открывать доступ к остальным. Разделение среды на небольшие зоны ограничивает распространение атаки.
</b></details>

<details>
